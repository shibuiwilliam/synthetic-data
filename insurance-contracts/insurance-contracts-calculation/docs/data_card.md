# docs/data_card.md — データカード（`dataset/data-card.md`）の仕様と自動更新

> `dataset/data-card.md` は **このデータセットの利用者が最初に読む 1 枚**である。
> 「何が・どれだけ・どうやって作られ・何に使えて・何に使えないか」を**実測値**で示す。
> **このファイル（docs/）が仕様の正本**で、`dataset/data-card.md` は
> `icc datacard update`（および `icc batch` / `icc generate`）が書き出す**生成物**である
> （`CLAUDE.md` 守ること 2。手編集禁止）。
>
> - 版: 1.0（2026-10-04 新設）
> - 実装: `src/insurance_contracts_calculation/export/datacard.py`、
>   CLI `icc datacard [update|check]`、テスト `tests/unit/test_datacard.py`、
>   測り方の検算 `scripts/verify_datacard.py`

---

## 1. なぜ要るか（ほかの説明ファイルとの分担）

このリポジトリには、既に説明にあたるものが 3 つある。**データカードは 4 枚目で、役割が重ならない。**

| | `README.md` | `DESIGN.md` | `icc export` の `DATASHEET.md` | `icc package` の `README`/`DATASHEET` | `dataset/data-card.md`（本件） |
|---|---|---|---|---|---|
| 生成 | 手書き | 手書き | `export_public()`（**1 文書**） | `distribution.build()`（**配布物**） | **`icc datacard update`** |
| 読者 | 開発者 | 設計を追う人 | 評価対象システムに課題を渡される人 | 配布先でカードを眺める人 | **使うかどうかを判断する人・引用する人** |
| 中身 | 使い方・中身の地図 | 設計の正本 | その文書の課題と約束ごと（正解は入らない） | 1 画面ぶんの要約 | **`dataset/` の規模の実測・内訳の全件・正解の中身・検証の結果・制限と偏り** |
| 重複の扱い | 使い方は README が正本 | 設計は DESIGN が正本 | 約束ごとは `taskcards.CONVENTIONS` が正本 | 配布面の要約はそちらが正本 | **カードは参照し、再掲しない** |

**どれも固定文字列に統計値を焼き込まない。** 焼き込むと、文書を足したときに嘘になる
（本体の `docs/decisions.md` 2026-10-04「`dataset/README.md` の生成ロジックが統計値を
固定文字列で焼き込んでいた」の再発防止）。

## 2. 絶対条件

1. **カードに出る数値はすべて `dataset/` の実ファイルから測る。** `TASK.md` §2.1 の表・
   `DESIGN.md`・過去のセッションの記憶を数値の出典にしない。
   例外は 1 つだけで、**「作れなかった組」は `dataset/_run_report.json` にしか無い**ので
   そこから読む。カードはその出所を明記する（§4.5）。
2. **データを足したら更新される。** 更新しないまま増えたら `make check` が赤くなる（§5）。
3. **人間の判断が要る欄を AI が埋めない。** 配布は `HITL.md` H4-b で「**配布しない。配布は
   人間が決定し、実行する**」と決まっている。カードはその決定をそのまま書き、変えない。
4. **母数の小さい観点を黙って隠さない。** 文書 3 本未満しか覆っていない観点（パターン・種目・
   スタイル・難易度の軸・表現手段）は、カード自身が「この観点で精度を語るには母数が足りない」
   と名指しする（§4.4）。
5. **正解が入っていることを隠さない。** `dataset/` には計算仕様・正解プログラム・正解表・
   全テストケースが入っている。カードは**学習に使わないこと**と、採点時に渡すものを絞る
   手段（`icc export`）を必ず書く。
6. **不合格・作れなかったものを隠さない。** 検証ゲートの結果は全文書ぶん集計し、
   作れなかった組は件数と理由の内訳を出す（§4.5）。
7. 生成は決定論。同じ `dataset/` なら同じカードが出る（`CLAUDE.md` 守ること 3。
   時刻・`uuid`・`hash()`・集合の反復順に依存しない。**自分自身のファイルサイズは数えない**——
   数えると書き出すたびに数が動き、鮮度検査が収束しない）。

## 4. 実装の決め

### 4.1 測り方

- 入力は `dataset/` 配下だけ。文書は `*/calc/manifest.json` の有無で見つける
  （`export/layout.py` の配置が正本）。
- **約款は素の JSON として読み、`core/docindex.py` の `Doc` で索引する。** 本体（`yakkan`）は
  import しない（`CLAUDE.md` 守ること 10、`tests/unit/test_discipline.py` が固定）。
  `policy.json` は `derived` を含む完成形なので、再計算も検証も要らない。
- 本文の文字数は `derived.plain_text[*].without_label` の長さの合計（本体 `manifest.py` と
  同じ定義。番号ラベルを含まない紙面の本文）。
- **同じ `policy.json` が複数のレイアウトに複製されている。** 各レイアウトの
  `source.json` は `policy.json` と同一（`calc/manifest.json` のハッシュが一致する）。
  約款側の要素は**文書ごとに 1 回だけ**数え、レイアウトの数で掛け算しない。
- **PDF の埋め込みフォントはページのフォント資源（`/BaseFont`）から読む。** 全文字を走査する
  方法（`page.chars`）と同じ結果になることは `scripts/verify_datacard.py` が別経路で突合する。
- 容量は `dataset/` の全ファイルを拡張子ごとに合計する。**`data-card.md` 自身は数えない。**
  ドットファイル・`__pycache__`・`.pytest_cache` も数えない（pytest を回すと増えるため）。
- 数値の整形は `{:,}`。容量は MiB 小数 1 桁（1 MiB 未満は KiB 整数、1 GiB 以上は GiB 小数 1 桁）。
- **所要時間の実測**：100 文書・280 レイアウト（2.2 GiB）で約 13 秒。内訳は `policy.json` と
  `layout.json` の読み込みが大半で、PDF のフォント資源の読み出しは 280 件で約 10 秒。
  `make check` に入れても支障のない範囲である（全文字走査なら 3 分半かかる。§5 の検算は別物）。

### 4.2 「宣言されているが使っていない」を挙げる

実装が持っている全体（宣言）と、`dataset/` に出ている実測を突き合わせ、**使用 0 のものを挙げる**。
出所は実装の登録簿で、カードに書き写さない。

| 観点 | 宣言の出所 |
|---|---|
| パターン（18 種） | `patterns/registry.py` の `ALL`（`id` と `title`） |
| 種目 | `packs/*.yaml`（`concepts.yaml` を除く） |
| プロファイル | `config.py` の `PROFILES` |
| スタイル | `config.py` の `EXTRA_STYLES` の値と、文書に出ている既定スタイル |
| 検証ゲート | `calc/manifest.json` の `gates` のキー（全文書の和） |
| テストケースの種別 | `calc/cases.jsonl` の `kind`（`example`/`boundary`/`unknown`/`random`） |

### 4.3 「足した分」と「既定の分」を分ける

約款側の要素（ノード・ブロック・定数）は、**計算規定として足した分**と**既定の約款にもともと
あった分**を分けて出す。足した分は `calc/patch.json` の操作（`add_node`・`add_block`・
`add_constant`・`add_term`・`add_index_row`）を数える。読み取りの難しさは既定の分にも依るので、
足した分だけを規模として語らない。

### 4.4 母数の小さい観点の自動検出

次の観点について「それを含む**文書**の数」を数え、**閾値（既定 3 文書）未満**なら §13 に
「母数が足りない」として列挙する。観点を増やしたら自動で検査対象になる。

- パターン（P01〜P18）・ルールの種別（calculation / decision）・配置（条 / 特約 / 別表）
- 表現手段（prose / formula / table / figure）・難易度の軸（`answer_key.json` の `difficulty`）
- 明示した事項（`spec.json` の `obligations`）・入力の型（int / bool / date / money …）
- 種目・プロファイル・スタイル

**文書数で見る**（本体のカードは content 数で見る）。拡張の 1 文書 = 1 つの `policy.json` ＋
1 組の正解であり、レイアウトが何本あっても正解は 1 組なので、文書が単位になる。

### 4.5 出所が `dataset/` に無いもの（1 つだけ）

**作れなかった組**（約款 × 何本目）は、試して落ちた記録なので出力の中に無い。
`dataset/_run_report.json` の `not_generated` から件数と理由の内訳を読み、
カードに「**出所は `_run_report.json`（生成時の記録）**」と明記する。
`_run_report.json` が無ければその項を落とす（嘘を書かない）。

**`_run_report.json` のほかの数値はカードに使わない。** 同じ数を `calc/` から測れるからで、
生成時の自己申告と実ファイルが食い違ったときに気づけるようにしておく。

## 5. 自動更新をどう担保するか（3 重）

| 層 | 仕組み | 効き方 |
|---|---|---|
| 生成 | `icc batch` の最後に `write_card()` を呼ぶ | データセットを作る本筋の経路で必ず更新される |
| 生成 | `icc generate` は、出力先に**既にカードがあるときだけ**更新する | `dataset/` に 1 文書足したときも追従する。カードの無い出力先（`examples/`・`out/`）は汚さない |
| 検査 | `make check` に `datacard-check` を足す | 更新を忘れたらコミット前に赤くなる（`dataset/` が無い環境では飛ばす） |

`icc datacard check` は**書き換えずに**食い違いを報告する（終了コード 1）。

**2 つの検査は別物である。**

| 検査 | 問い |
|---|---|
| `icc datacard check` | カードは**いまの `dataset/` から生成したもの**か（鮮度） |
| `python scripts/verify_datacard.py` | **測り方そのもの**が正しいか（`datacard.py` を使わない別経路で再計算して突合） |

前者は `make check` に入っている。後者は測り方を変えたとき（節や項目を足したとき）に手で回す。

## 7. 変えるときの注意

- **節を増やすときは「数値の出所」を §3 の表に書いてから実装する。** 出所の無い数値を
  カードに書かない。
- 固定文に数値を書きたくなったら、それは `DataCardStats` に足すべき項目である。
- 観点（§4.4）を足したら `scripts/verify_datacard.py` の突合表にも足す。
- 配布・ライセンス・引用のしかたは**人の領域**（`HITL.md`）。決定が変わるまで固定文を書き換えない。
