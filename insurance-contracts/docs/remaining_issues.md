## R1 検索 qrels の部分適合が薄い

### 実測

| クエリ種別 | grade 2 | grade 1 |
|---|---|---|
| heading | 640 | **9** |
| term | 352 | **0** |
| scoped | 78 | **0** |
| qa | 1,267 | 308 |

**適合が 1 件だけのクエリが 1,071 / 1,549（69%）。** これでは nDCG がほぼ二値になり、
順位の良し悪しを測る分解能が出ない。ランク学習の学習信号としても弱い。

### 原因（2 つ）

1. **citation の突合が完全一致になっている**（バグ）。
   表・図のパッセージの `citation` は**導入文の項**（「第1章 第1条 (1)」）から取るが、
   条のパッセージは「第1章 第1条」。前方一致で見るべきところを完全一致で見ていたため、
   369 件の表・図のうち条と結びついたのは **15 件だけ**だった。
2. **grade 1 の供給源が「同じ条の別の項」しかない。** `derived` には他にも
   機械的に導ける関係があるのに使っていない。

### 対処（**関係は derived に実在するものだけを使う。適合度を捏造しない**）

| クエリ種別 | grade 1 にするもの | 根拠 |
|---|---|---|
| term | その語を `{term:}` で実際に使っている要素を含むパッセージ | `derived.term_uses` |
| term | その語を行見出しに持つ定義表のパッセージ | 定義表のセル |
| heading | その条に属する表・図（**前方一致で直す**） | `citation` の前方一致 |
| heading | その条を `{ref:}` で参照している条 | `derived.refs`（to_id が当該条） |
| scoped | その文書の、その条に属する表・図 | 同上 |
| qa | evidence の条を `{ref:}` で参照している条 | `derived.refs` |

grade 1 が増えすぎると評価が緩くなるので、**1 クエリあたり grade 1 は 20 件まで**に切る
（`citation` の近い順）。

## R3 `answer.json` の二重持ち

### 実測（34 文書の合計）

| ファイル | 合計 |
|---|---|
| `answer.json` | **42MB** |
| `source.json` | 16MB |
| `layout.json` | 20MB |
| `pages/*.png` | 213MB |
| 全体 | 335MB |

`answer.json` は `source` と `layout` を**丸ごと内包**しているので、**36MB が重複**している。
バイト数だけなら PNG が支配的だが、問題は容量よりも
**「同じ正解が 3 か所にあり、どれが正か利用者に分からない」**こと。

### 対処

`answer.json` からは `source` / `layout` を**落とす**（同じディレクトリに実体があるので参照で足りる）。
代わりに `yakkan.answer.load_answer(dataset_dir)` を用意し、3 ファイルを読んで
`Answer` を組み立てる。**メモリ上の `Answer` の形は変えない**ので、
`qa` / `eval` / `export` のコードは読み込み方だけ差し替えれば済む。

## S2 「表1-1」と「表1」の同居（R4 の積み残し）

`caption_numbering: chapter` のとき、章の外（別表・前付け）の表・図は通し番号のままなので、
group-0002 では `表1-1` `表1-2`（章の中）と `表1`（別表の中）が同居している。

前回は「書式で区別できる」として見送ったが、**読み取りの正解としては紛らわしい**。
「表1」を読み取ったモデルが、章の中の「表1-1」を指しているのか別表の表を指しているのか、
文字列だけからは決められない。

### 対処（**実物に従う**）

参考 #14 では、**別表の中の表に番号は振られていない**（別表そのものが「別表N」の番号を持つ）。
`caption_numbering: chapter` のときは、**章に属さない表・図に番号を振らない**ことにする。

番号が無い表は `{ref:}` の参照先にできないので、
**L01 を「キャプションはあるが番号が無い表・図を参照したらエラー」に直す**（現在は
キャプションの有無だけで判定しており、build が `BuildError` で落ちる）。

### 実施（2026-09-22・完了）

- `assign_caption_labels` は `caption_numbering: chapter` のとき章に属さない表・図に
  番号を振らない。`derived.tables[].caption_label` は `null` になる（要素は残る）。
- `LintContext.caption_labels` を足し、L01 の参照先判定を「キャプションの有無」から
  **「build が実際に番号を振ったか」**に変えた。章の外を参照すると専用の文言で error。
- 描画側は `_captioned()` を通し、番号が無いときは全角空白の区切りを出さない
  （出すと `plain_text` と食い違って V03 が落ちる）。
- 影響したのは group-0002 の `tbl_app1_severe` 1 件のみ（`表1` → 番号なし）。
  参照している箇所は無かった。再描画して verify・qa とも error 0。
  文中に残る「表1」はすべて**別表1**（別表そのものの番号）で、衝突しない。

## S6 自己評価が循環している

`yakkan eval --oracle` は `answer.json` から予測を作るので、**ハーネスの自己整合**しか示さない。
`degrade()` の崩し方も機械的（文字を確率で落とす・行を落とす・citation を空にする）で、
**現実の読み取りが起こす誤り**とは違う。

現実の誤りの例：
- 文字の**置換**（「第1条」→「第l条」、全角半角の揺れ、similar-glyph）
- 表の**行の結合・分割**（結合セルの展開に失敗する）
- 見出しの**取りこぼし**（小さい見出しを本文と誤認する）
- 読み順の**段組の取り違え**（左段と右段を交互に読む）

**対処**：`degrade()` にこれらの崩し方を足し、
**崩しの強さに対して指標が単調に悪化すること**をテストで固定する。
指標が壊れていれば（たとえば正規化しすぎて誤りを吸収してしまえば）単調性が崩れるので、
循環しない検証になる。

### 実施（2026-09-22・完了）

`degrade()`（粗い崩し）は残し、**`misread()`** を足した。`yakkan eval --oracle --misread 0.3`。

- 字形の取り違え（「口」と「ロ」など、**NFKC で吸収されない**組み合わせだけ）と脱字
- 表の行の結合（対を (0,1) (2,3) … に固定）と端の列の取りこぼし
- 見出しの取りこぼし（項・号は重み 1.0、章・条は 0.3）
- 構造位置の浅い読み（「第2章 第1条 (1)」→「第2章 第1条」）
- 段組の取り違え（ページの前半と後半を交互に読む）
- 図のノード・エッジ・経路の取りこぼし

**入れ子にするのがこの設計の肝**。`_Dice` が先に一様乱数を引いてから `rate` と比べるので、
`rate=0.1` で壊れた箇所は `rate=0.3` でも壊れる。引く回数を `rate` に依存させると
（条件式の短絡、間引いた要素の draw を飛ばす）乱数列がずれて単調性が壊れる。
実際に最初の実装がこれで τ と QA が単調に下がらなかった。

**単調性は recall で見る。** 要素を落とすと誤りも一緒に落ちて precision が上がり、
F1 は跳ねる（jyusetsu-0001 で 0.8571 → 0.9 の実例）。

**反応の有無は文書によって違う。** 6 文書 × 4 seed で確かめたところ、
単調性の違反は **0** だったが、`path_f1` が rate 0.7 でも動かない組み合わせが 5 件あった。
図が 1〜2 本しかない文書（jyusetsu-0001・group-0002）で、経路を落とす抽選が
一度も当たらなかったためで、指標の欠陥ではない。テストは図が 5 本ある文書で回す。
