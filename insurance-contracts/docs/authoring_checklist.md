# authoring_checklist.md — 執筆前・執筆後に必ず確認すること

P4-c で 7 文書を書き、reviewer を全文書に通して得た教訓。
**新しい content を書くときは、着手前にこの全文を読むこと。**
`docs/style_guide.md`（文体）と `docs/schema.md`（型）を置き換えるものではなく、
「lint が通っても残る欠陥」を潰すための追加チェックリスト。

## 1. 転載（§0.4-1）— いちばん重い違反

P4-c では **5 文書で同じ形の違反が再発した**。lint は検出できない。

### 模倣は「文章」より先に「数値の列」と「列挙の順序」に出る

実際に見つかった違反：

- 後遺障害等級表の支払割合が実在の数列そのまま（12 個すべて一致した例がある）
- 障害の程度の文言が法令別表の逐語（等級だけ入れ替えて使っていた）
- 高度障害状態表の 6 項目が、区分立て・語順・語尾まで実物と一致
- 地震保険の支払割合・損害割合・全損みなしの基準値が実物そのまま
- 手術給付倍率の階層（大きい順に 3〜4 段）と代表値が実物と一致
- 戦争免責・暴動の定義・示談代行条項・自動車取扱業者免責の**列挙の語彙と順序**
- 常用漢字外を避けた交ぜ書き表記まで実物の慣行と一致していた（表記の癖も指紋になる）

### 対処

- **別表の数値は必ず自分で作り直す。** 等差・等比にしない（作り物に見える）。
  端数を混ぜ、段数も実物と変える（12 段 → 8 段など）。
- **別表特有の語形を使わない。** 「…以上で失ったもの」「…の用を廃したもの」
  「終身常に介護を要する」は、それ自体が指紋。機能記述（「…の機能が永続して失われた状態」）に置き換える。
- **判定軸ごと変える**のがいちばん確実。例：「常に介護を要する」→「日常生活動作○個以上の介助」。
- 業界共通で避けられない定型（「…をいいます。」「ただし、…を除きます。」）は問題にしない。
  問題は、特定の会社の約款でしか使われない言い回し／実在商品の構成そのまま／実在の特約名。
- **迷ったら列挙の順序を入れ替え、語彙を 1 つ以上差し替える。**

### 書いたあとの自己点検

書き終えたら、別表と免責の列挙を読み返して「これは実物で見た形か」と自問する。
見覚えがあるなら、それが模倣の証拠。

## 2. 正解データ（gold）自体の誤り

`facts` と `alt` は **QA の正解そのもの**。間違っていると評価が壊れる。

- 図の `facts` に「◯◯は四つに分かれる」と書いたら、**本文を数えて確かめる**
  （実際に「四つの節」と書いて 6 節だった例、「四つの部分」と書いて 5 章だった例がある）。
- 図のノードラベルと本文の章題を一致させる。図だけ短縮した名前にしない。
- 図と算式の中でも `{const:}` `{term:}` `{ref:}` が使える（2026-09-22 から）。
  **数値は必ず `{const:}` で書く。** `alt`・`facts`・目盛・区間の端も含めて解決される。
  生文字列で書くと定数を変えたときに取り残される（実際に 4 文書で起きた）。
  太字・ルビ・改行・脚注は SVG に形が無いので L06 が弾く。

## 3. 表・図は「導入文を持つ項の blocks」に入れる

条（article）直下の `blocks` に置くと、**導入文より前に描画される**。
「下表のとおり」が 2 段落上の表を指す状態になり、読み順・アンカーの QA が全滅する。
`dataset/<doc_id>/layout.json` の `pages[].reading_order` で順序を確認できる。

## 4. `meta.constants` の値を散らす

同じ値が複数の概念に使われていると数値 QA の弁別力が無くなる
（30 日が 4 概念、60 日が 3 概念という例があった）。

- 同一値の重複は **最大 2 件**まで。
- 宣言しただけで使わない定数を残さない。
- 本文にハードコードした数値を残さない（`{const:}` を通さないと L11 の検査が効かない）。
- **実在商品の代表値を避ける**（弁護士費用 300 万円、法律相談 10 万円、自賠責の慰謝料日額など）。

## 5. 表と条文の対応を空振りさせない

一覧表が掲げる保険金・補償には、**必ず対応する条文を置く**
（一覧に 5 つ挙げて条文が 3 つしかなかった例がある）。
逆に、条文で定めた限度額は一覧表にも出す。

## 6. 定義語

- 定義した語は本文で**実際に使う**（L12 が拾うのは未定義語だけで、死語は拾わない）。
- 同じ語を 2 か所で違う内容に定義しない（定義表と脚注で食い違った例がある）。
- 定義の基準者をそろえる（「記名被保険者と同居の親族」と定義しておいて
  「保険契約者の同居の親族」と書くと、定義がその場合をカバーしない）。
- 章ごとに呼称を変えない（「ご契約のお車」と「被保険自動車」が章で割れていた例がある）。
  条文は `{term:}` に統一し、くだけた呼称は欄外注と前付けに限る。

## 7. 文体の切り分け

- 依頼形（「…してください」）を使ってよいのは **欄外注 `box` と前付け・表紙 notes だけ**。
  条文・脚注・表注・表頭では「…しなければなりません」「…するものとします」。
- life は第 1 編（しおり）だけが平易な敬体。第 2 編以降は条文体。
- teikan は全編が常体。

## 8. `{ref:}` は「意味が合っているか」まで見る

lint は参照先の**存在**しか見ない。参照先の条が参照元の主張と合っているかは人が見る。

- 「…の取扱いは第 3 項のとおり」と書いて、実際は第 4 項にも書いてあった例
- 取締役会の招集順序を、総代会の議長の条で代用していた例
- 「別表に定める」と素の文字列で書き、別表が 3 つあってどれか決まらなかった例
  → **別表への参照も必ず `{ref:app1}` で書く**（§7.4 は手書きの参照を禁じている）

## 9. `records` を付ける

参照表（definitions / benefit_schedule / grade_schedule / surgery_schedule / rate /
plan_matrix / procedure / rider_index / purpose_index / history）は
`grid` と `records` の二重表現を持つ（CLAUDE.md §2-4）。lint L05 が warn を出す。

    uv run python scripts/fill_records.py content/<cid> --write

結合セルのある表（定義表の五十音列・等級表）は機械導出できないので**手で書く**。
列挙表（enumeration / exclusions）は参照表ではないので不要。

## 10. 業法・実務と矛盾させない

- 相互会社の剰余金処分・社員配当は**総代会**の決議（取締役会ではない）。
- 相互会社の特別決議は「総代の半数以上・議決権の 4 分の 3 以上」（3 分の 2 は株式会社の閾値）。
- 賠償責任保険の免責は原則「故意」のみ。重過失・無免許・酒気帯びは車両保険や傷害系に及ぼす。
- 告知義務違反解除には「因果関係不存在」の特則（保険法の片面的強行規定）を必ず置く。
- 対人賠償は自賠責超過部分に限る旨を書く。

## 描画で踏む罠（内容の問題ではない）

- **`RenderLayoutError`（WeasyPrint の AssertionError / IndexError）**：
  本文の字数を数十字ぶん増減させると通ることが多い。ただし**構造を変えないと通らない形もある**。
  自分の書いた文が悪いと思って探索しすぎないこと。
  対処の順序：(1) 字数を増減、(2) 項の分け方を変える、(3) 別の style で描く。
- **段組の中で `span_columns: true` を使わない。** 収まらないと後続が黙って消える。
  現在は `render` が欠落を検出して止まるが、そもそも使わないのが安全。
- **「レンダリングが成功した」は「内容が全部載った」を意味しない。** 必ず `verify` を見る。
- 横長の表は列数を減らすか、行見出しの語を短くして段内に収める。
- 図の `timeline` の軸目盛ラベルは両端に寄せて描かれる（7 文字でも切れない）。
- `matrix` の列幅は列見出しに合わせて広がる。

## 既知で、追わなくてよいもの

報告が重なっているが**測ったうえで現状が最善**と判断したもの。直そうとしないこと。

- **ヘッダの章名がページ冒頭の内容と食い違うことがある。** 全13データセット242ページで測ると、
  現行の `string(chapter, first)` は「そのページの本文の主の章」と 87.6% 一致する
  （代替の `start` は 53.7%）。残る 12.4% は「ページ途中で次章が始まり、前半が前章」のページで、
  実物の約款でも起こる。`docs/decisions.md` 2026-09-22。
- ~~表番号がキャプション無しの列挙表を数えて飛ぶ~~ → **2026-09-22 に解消済み**。
  キャプションのある表・図だけに番号が振られる。列挙表に番号は付かない（実物どおり）。
- **rowspan がページ／段の境界をまたぐと継続側のセルが空欄になる。** A5。読み取り課題としては妥当。
- **表紙にページ番号とフッタが出る。** B2。

## QA を書くときの型の選び方

`extract` / `table_lookup` / `definition` は **answer が evidence の平文に含まれていること**が
L14 で検査される。要約した答えや算出値を書くとエラーになる。

| 問いの形 | 型 |
|---|---|
| 本文・表から**そのまま**引ける | `extract` `table_lookup` `definition` |
| 表の中で**比べる**（最大・最小・どちらが大きい） | `table_reason` |
| 場面を与えて**規定を当てはめ、値を導く** | **`apply`** |
| 図の経路・隣接 | `figure_path`（答えは図に**実在するラベル**でなければ L14 が落とす） |
| 図の記述の真偽 | `figure_fact` |
| 参照先 | `crossref` ／ 数 | `count` ／ 存在しないもの | `negative` ／ ページ | `locate` |

`apply` の例：「入院保険金日額が５，０００円のご契約で胃の切除の手術を受けたとき、
手術保険金の額は何円か」→ 別表の給付倍率を引いて掛ける。**自動生成はしないので、
場面適用型は執筆 QA でしか作れない。** 1 文書に 1〜3 問入れると評価の幅が出る。

### 執筆 QA の配り方は L16 が強制する（2026-09-22 から）

文章で書いただけでは守られず、30 content のうち 13 content が違反していた
（`apply` なし 11／図の問い 3 問未満 4／表の問い 3 問未満 2／件数が 15 でない 2）。
`yakkan lint content/<cid>` の **L16** が次を error にする。

| 条件 | 理由 |
|---|---|
| 件数がちょうど 15 問 | CLAUDE.md §15 の決定 |
| `table_lookup` ＋ `table_reason` が 3 問以上 | 表の読み取りは自動 QA だけでは浅い |
| `figure_path` ＋ `figure_fact` が 3 問以上 | 図は自動 QA が経路までしか作れない |
| `apply` が 1 問以上 | **自動生成できない唯一の種別** |
| `evidence` と `question` が空でない | L14 の前段 |

## 組み立てヘルパ `scripts/authoring.py`

parts の JSON を手で書くと、セルの id・`rowspan`・`records` を取り違えやすい。
`scripts/authoring.py` に、表・列挙表・五十音の定義表・条の組み立てを置いてある。

| 関数 | 作るもの |
|---|---|
| `C` / `merged` | セル 1 つ／結合セルに飲み込まれた位置 |
| `table` | 見出し行 1 行の表（`records` も一緒に作るので `header_path` が取れる） |
| `h2table` | **2 段ヘッダ**の表（特約一覧・プラン比較マトリクス。結合と `records` を自動で組む） |
| `box` / `formula` / `par` | 囲み（`margin_note` / `caution` / `note`）／算式（`inline_boxes`）／段落ブロック |
| `defined_terms` | (id, 語, 定義, 索引かな) の並びから `defined_terms` と `kana_table` の材料を作る |
| `enum_table` | 文と一体の列挙表（番号欄は `{auto_label}`。**キャプションを付けない**） |
| `kana_table` | 五十音の索引列を持つ定義表（索引列は行を結合） |
| `art` / `jart` | 条（項・号・条末脚注・ブロック）／重要事項説明書のバッジつき大見出し |
| `write` | UTF-8・indent 2・末尾改行で書く |

```python
from scripts.authoring import art, enum_table, table, write

write(
    "content/foo-0001/parts/ch1.json",
    {
        "id": "ch1",
        "kind": "chapter",
        "title": "補償条項",
        "children": [art("ch1_a1", "保険金を支払う場合", ["当会社は、…支払います。"])],
    },
)
```

**検証はしない。** 書いたら `uv run yakkan lint content/<cid>` を必ず通す。

## 仕上げの手順

    uv run yakkan lint content/<cid>          # error 0 / warn 0 にする
    uv run python scripts/fill_records.py content/<cid> --write
    uv run yakkan build content/<cid>
    uv run yakkan render content/<cid>        # style 省略時は blueprint の既定
    uv run yakkan verify dataset/<doc_id>     # error 0 / warn 0 にする
    uv run yakkan qa dataset/<doc_id>         # 自動 QA 30 問＋検証
    uv run yakkan manifest update

環境変数 `DYLD_FALLBACK_LIBRARY_PATH=/opt/homebrew/lib` が要る（macOS の Pango）。

**最後に PNG を全ページ自分で開いて見る。** ページ数と lint が通っても崩れていることはある。

## 表・図を `{ref:}` で参照できる（2026-09-22 から）

キャプションのある表・図は `{ref:tbl_coverage}`「表２」、`{ref:fig_flow}`「図１」と書ける。
**素の文字列で「表２」と書かない**（番号は build が振るので、表が増減するとずれる）。
キャプションの無い列挙表には番号が無いので参照先にできない。参照したいならキャプションを付ける。

## 特約は `kind: "rider"` で書く（2026-09-22 から）

特約は普通保険約款の章ではない。`kind: "rider"` にすると番号が付かず、中の条は
特約ごとに第１条から始まる。参照は題名で解決される（「携行品損害補償特約第３条（補償内容）」）。

- 「○○特約（{ref:rider_xxx}）」と書くと題名が二重になる。**`{ref:}` だけで書く。**
- 特約の中から普通約款を指す参照は従来どおり（「第２章第１条」）。
- 準用の条は「普通保険約款の規定を準用します」でよい。章番号を数えなくてよくなった。
- 生保の「第３編　特約条項」のように部の下に置く形でも `rider` を使う。

## 定款（teikan）の番号（2026-09-22 から）

- 列挙表の号は `（１）（２）`（①②ではない）。
- 附則は「附則 → 第１　施行期日 → １／２」。項は裸の数字。
- `{ref:}` は章を冠さない（「第１４条（決議）」）。附則の中を指すと「附則第３」。

## 2026-09-22 に足したジャンルの書き方

- **`golf`（賠償責任保険 約款集）**：番号方式は損保と同じ。脚注は多め（10 件以上）。
  版面が 202×188mm と小さいので、横長の表は列を減らす。
- **`group`（団体保険）**：`meta.article_heading = "above"` なので、**条見出しは条の上に括弧書き**で出て、
  条ラベルは第1項の本文の先頭に走り込む。条末の注記は「第N条　備考」の枠（黒丸数字 ❶）。
  **項・号への参照は「第1項」「第1項第4号」と解決される**（印字は無番号でも、参照は書き下す）。
- **`jyusetsu`（重要事項説明書）**：**条を使わない。** 大見出し ›（N）› ① の 3 階層で、
  `article` ノードが丸数字の小見出しになる。見出しには `badges` を付ける
  （「契約概要」＝商品の内容、「注意喚起情報」＝不利益になる事項）。**両方付く見出しもある。**
  別表は持たない。`{ref:}` はほとんど使わず、「②（主な補償の概要）」のように項目名で示す。
