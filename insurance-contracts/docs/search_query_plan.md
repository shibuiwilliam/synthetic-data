### 計画作成中に設計が変わった 3 点（推敲の結果）

害がある**ことが実測で分かった。本計画では次のように改める。
**設計書の冒頭と `docs/decisions.md` には 2026-10-03 に追記済み**（R-8 は解消）。

| # | 設計書の記述 | 実測で分かったこと | 本計画での扱い |
|---|---|---|---|
| **AA-4** | 「`term` の grade 1 の文書限定（`doc_id not in docs`）を撤廃する」 | **`term_id` は文書をまたいで一意でない。** 70/502 の id が別の語に使い回されている（`pet` は「いえのおまもり」「対象動物」など 11 語、`desk` は 8 語）。素朴に撤廃すると grade 1 が 6,816 件の正解に対し **3,601 件（35%）の誤り**を含む | **撤廃しない。** 代わりに**文書ごとに `term_id` を解決する**バグ修正にする（現状でも 13 件の誤ラベルがある）。頻出語の再現率は AA-6 の `enumeration` で担保する（W3・W7） |

### 段 1 — 欠陥修正（方針に依存しない。これをやらないと以降の数値が読めない）

#### W1 AA-1 `qa` の gold の誤配を直す　｜状態：**完了**　｜**最優先**
- **原因**：`_passage_of_element()` が `element_id → passage_id` の索引を**コーパス全体で 1 本**作り
  `setdefault` で先着順に埋めている。`element_id` は文書内でしか一意でない
  （1,517 種が衝突。`par_colophon_1` は 89 文書、`ch2_a1` は 80 文書）。
- **変更**：`yakkan/search_set.py`
  - `_passage_of_element(passages)` → `_element_index(passages) -> dict[str, dict[str, str]]`
    （`doc_id` → `element_id` → `passage_id`）
  - `_resolve_evidence(evidence, index)` の `index` を**その文書ぶんだけ**にする
  - `build_search_set` の `qa` ループで `index = element_index.get(doc_id, {})` を使う
- **受入**：`probe` §3 の誤配が **2,916/3,819（76%）→ 0**。
  `qa` の `n_exact` 合計が減らない（gold が消えるのではなく正しい文書に移る）。
  `probe` §2 の「gold が食い違う同一文字列クエリ」が 472 → 0。
- **テスト**：T-1

#### W2 AA-2 見出し名から番号ラベルを落とす　｜状態：**完了**
- **原因**：`（…）` の括弧内を抜く規則だけなので、括弧を持たないしおり部の見出し
  （`① お引受けの判断`）は `title` 全体がクエリになる（**173 件**）。
- **変更**：`yakkan/search_set.py` に `_heading_name(title) -> str | None` を新設。
  丸数字（`[①-⑳]`）・`第N条` `第N章` `第N節`・先頭の `（N）` `N.`・前後の全角空白を落とし、
  残りが 3 字未満なら `None`（クエリにしない）。
  **既存の正規表現を使う**——`yakkan/lint/` の L03（番号ラベル直書きの検出）が同じ形を持っているので、
  共通の定数に切り出してから使う（二重実装を作らない。R-A の観点）。
- **受入**：クエリ文の番号ラベル混入が **173 → 0**。
  見出し名が 976 → **950 種**（26 種はラベルを落とすと 3 字未満か他の見出しと同名になる）。
- **テスト**：T-2

#### W3 AA-4 `term_id` を文書ごとに解決する　｜状態：**完了**　｜**設計書から変更（§0 参照）**
- **原因**：grade 1 を `wanted = term_ids[語]`（**全文書の `term_id` の合併**）と
  `passage.terms_used` の積集合で決めている。しかし `term_id` は文書ごとに独立で、
  **70/502 の id が別の語に使い回されている**（`pet` は 11 語、`desk` は 8 語）。
- **いま起きている誤り**：13 / 3,371 件（0.4%）。
  文書限定（`doc_id not in docs`）が被害を抑えているだけで、規則としては誤っている。
  **設計書どおり文書限定を撤廃すると、誤ラベルが 3,601 件（35%）に膨れる**（実測）。
- **変更**：`doc_id → {term_id: 語}` の表を作り、
  grade 1 は「**その文書で**その語に割り当てられた `term_id` を使っているパッセージ」に限る。
  文書限定はそのまま残す（素のクエリは `df_docs == 1` なのでそもそも 1 文書に閉じる）。
- **受入**：誤ラベル 13 → **0**。grade 1 の総数がほぼ変わらない（13 件減るだけ）。
- **テスト**：T-3

#### W4 AA-15 定義パッセージを紙面に対応づける　｜状態：**完了**　｜**今回の調査で発見**
- **原因（2 つ）**
  1. `definition` パッセージ（1,230 件・コーパスの 14%）は `element_ids=[]` `pages=[]` `citation=""` で
     **紙面上の位置を持たない**。`defined_terms` は `{term:}` 解決用のメタデータで、
     テンプレートから参照されておらず**描画されていない**。
  2. 定義文は実際には**定義表**（`semantic_type: definitions`）の行として印字される。
     表は別のパッセージなので**同じ定義文が 2 つのパッセージに重複**し、
     `term` クエリの gold は**印字されない側だけ**を指す。
     → **`term` クエリ 506 件のうち 475 件（94%）で、ほぼ同じ定義文を持つパッセージが grade 0**。
     紙面に出ている方（表）を返した検索器が誤答と採点される。
- **先例**：`outline` から紙面に出ない節点を外した（`docs/remaining_issues.md` T7）、
  列挙用の表を採点対象に戻した（Z2）。**「紙面に出ないものを正解にしない」**を適用する。
- **変更**：`yakkan/search_set.py` の `build_passages`
  1. `semantic_type: definitions` の表を、**行ごとに 1 パッセージ**（`kind: definition`）に割って**足す**。
     `passage_id` は `<doc_id>::<table_id>__r<N>`、`element_ids` はその行のセル id
     （`tbl_definitions__r1c0` …）、`pages` はそこから、`citation` は表の持ち主の条。
     `title` は見出し列（`role: stub`）のセル＝用語。
  2. **表のパッセージは残す**（**定義表を `evidence` にする QA が 354 問ある**ので消せない）。
     `term` クエリでは行パッセージを grade 2、表パッセージを **grade 1**（粒度の粗い関連）にする。
  3. `passage_id` が `::term::<id>` の**論理パッセージは出さない**。
     紙面に出る語は行パッセージが代わりになる。
  4. 定義文が紙面のどこにも出ない語は**クエリにしない**（語の文字列で **30 種**・用語の実体で 125 件。
     `life` 9 content に集中し `auto-0007` に 1 件）。
- **実測の裏づけ**：用語 1,230 件のうち定義表の行として印字 **1,115 件（91%）**、
  定義文が紙面に出ない **125 件（10%）**。語の文字列では 506 種のうち **30 種**が全文書で紙面に出ない。
- **受入**：`definition` パッセージの `pages` が**全件非空**。
  定義文の二重化による grade 0 が **475 件 → 0**。`term` クエリが 506 → **476 種**。
  パッセージは **8,561 → 約 8,450**（定義表 77 枚の行 **1,117 件**を足し、`::term::` の 1,230 件を外す）。
- **リスク**：`passage_id` が変わる（`::term::driver` → `::tbl_definitions__r1`）。
  → `id_map.json`（W11）に**パッセージ id の対応も入れる**（§6 R-4）。
  `life` は定義表を持たないため `life` の `term` クエリが減る → §5.5 でジャンル分布を確認。
- **テスト**：T-4

#### W4b（任意・本計画では実施しない）`life` に定義表を足すか　｜状態：**保留**
`life` 9 content が定義表を持たないのは blueprint の必須要素に無いため。足すと
**9 content の再執筆・再 render** が要り、20 ページ上限に当たる恐れがある。
