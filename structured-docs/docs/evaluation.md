## 2. 継承する成果物と指標（全ファミリー共通）

### 2.1 文書ごと・全体の評価向け成果物

| ファイル | 内容 | スキーマ |
|---|---|---|
| `elements.jsonl` | 1 行 1 要素の平索引。**評価スクリプトが最初に読む唯一のファイル**。kind・citation・parent_id・page・bbox・本文・表セルの意味座標・図ノードを 1 か所で引ける | `schema/element.schema.json` |
| `dataset/search/passages.jsonl` | 検索登録単位（条 1 パッセージ・長い条は項で分割・表 1 パッセージ・**定義表は行ごとにも**・図は alt＋facts・逐条解説は `kind: commentary` の別パッセージ）。**コーパスは content ごとに 1 スタイル** | `schema/passage.schema.json` |
| `dataset/search/queries.jsonl` | **10 種**（§7）。`filters` はクエリの一部。打ち切りは `related_truncated` / `n_related_total` に記録 | `schema/query.schema.json` |
| `dataset/search/qrels.jsonl` | grade 2（答えがそこにある）/ 1（関連。1 クエリ 20 件で打ち切り・文書横断で均等に拾う） | `schema/qrel.schema.json` |
| `dataset/README.md` | 読み方（ファイル構成・座標系・採点コマンド）。`docsynth export` が**実測値を埋め込んで**生成する | — |
| **`dataset/data-card.md`** | **データカード**（規模・内訳・作り方・品質保証・制限と偏り・ライセンス）。`docsynth datacard update`。仕様は `docs/data_card.md` | — |
| `dataset/manifest.json` | 全文書一覧＋成果物一覧＋checksums。`docsynth manifest check` が鮮度を検査し `make check` に入れる | — |

**`README.md` と `data-card.md` の分担**：前者は「使用説明書」（これから評価コードを書く人）、
後者は「成分表示」（使うかどうかを判断する人・引用する人）。**どちらも統計値を固定文字列に焼き込まない。**

### 2.2 読み取りの指標（`docsynth eval`。13 指標）

ページ別 CER／outline F1（label・title・page・citation・kind）／構造位置 coverage・citation 正解率
（**厳密一致と包含 `_contains` の併記**）／表 TEDS＋セル値 F1（header_path 経由の 3 つ組）／
図ノード・エッジ・経路 F1／列挙の順番つき一致／読み順 Kendall τ／bbox IoU（＋当たり率）／QA 一致。

### 2.3 検索の指標（`docsynth eval --search-run`。8 指標）

| 指標 | 何を見るか |
|---|---|
| nDCG@1/5/10 | 順位の良さ（grade 2＝2・grade 1＝1 の利得） |
| Recall@1/5/10 | 取りこぼし |
| **`exact_recall@k`** | **grade 2 だけ**の再現率（出題元を grade 1 に戻した kind で、字面一致の下駄を外して見る） |
| **`r_precision`** | 適合件数 R で切ったときの精度（`enumeration` の主指標） |
| MRR | 最初の正解までの距離 |
| **`doc@1`** | 1 位が**正しい文書**か（パッセージを外しても文書は当てられているか） |
| **`confusion@k`** | 紛らわしい非適合（同名見出し・同義語）を何件引いたか |
| **`false_positive_rate`** | `no_answer` クエリで何か返してしまった率 |

- **`recall_ceiling@k`（到達可能上限）を必ず併記する**（適合が k 件を超えるクエリでは満点の並びでも 1 に届かない。yakkan T2）。
- **クエリの `filters` はクエリの一部**。何を索引したか（本文だけ／メタデータも／図の alt も）は
  実行側が `index_setting` で申告する。申告の無い run は採点しない。
- クエリ種別ごとと全体の両方を出す。**ファミリー別にも出す**（§6）。

### 2.4 コマンド

```
docsynth eval dataset/<doc_id> --pred pred.json       # 1 文書の採点
docsynth eval dataset/<doc_id> --oracle [--misread R] # 自己評価（満点／崩した満点）
docsynth eval --all --oracle                          # 全文書
docsynth eval --all --pred-dir <dir>                  # <doc_id>.json を拾って全文書＋平均
docsynth eval --oracle --dump-pred <out>              # 正解から「予測の実例」を出す（§4）
docsynth eval --search-run run.json                   # 検索の採点
docsynth export                                       # elements.jsonl / passages / search / README / data-card
docsynth datacard update|check                        # データカードの生成・鮮度検査
```

## 3. 採点の原則（姉妹で確定済み。変えるときは decisions に記録し、前後の `eval --all --oracle` を添える）

1. **突合はすべて中身で行う**。予測に内部 id は無い前提（QA のみ id）。テキストは正規化一致
   （NFKC＋空白除去）、見出しは (label, title)＋**出現回数**（同名見出しの取り違え防止。yakkan S7。
   「（目的）」「（定義）」「（協議）」はファミリーを横断して大量に重複するのでこれが効く）、
   表・図は caption_label を**正規化してから**突き合わせる（全角「表１」と半角「表1」。yakkan X3-3）。
2. **表の対応づけは「キャプション → 中身 → 位置」の 3 段**で行う（keiyaku V-E：位置だけで対応づけていたため、
   予測に余分な表が 1 つ入るだけで TEDS が 0.36 に崩れた）。
3. **構造位置の coverage は gold 1 件につき 1 回まで数える**（同じ citation に予測が複数当たると
   coverage が 1 を超えていた。keiyaku V-C）。
4. **列挙の採点は中身で突合する**（citation 一致に依存させない。項目を完全に読めているのに 0 点に
   なっていた。keiyaku V-C）。
5. **図のノードは `id` を任意とし、ラベルを鍵にする**（`id` 必須だと省いた予測の全ノードが
   1 件に潰れた。keiyaku V-D）。
6. **citation に run-in ラベルを含めない**（約款型の条見出しが本文に走り込む体裁で
   「第三条 第三条 (1)」のような**外から再現できない正解**ができていた。keiyaku V-D）。
7. **列挙として組んだ表は tables の母数に入れない**（enumerations 側で採点。二重に求めない。yakkan X3-1）。
8. **列挙の項目は行頭番号を付けても付けなくても正解**（採点前に両側から落とす。**NFKC の前に**落とす。yakkan T8）。
9. **予測の全キーは任意**。無い観点は 0 になるだけで他は採点される。壊れた予測は黙って 0 点にせず、
   形の違いを警告として出す（yakkan W3）。
10. 自己評価の崩し（misread）は**入れ子**にし、崩しの強さに対して指標が recall で単調に悪化することを
    テストで固定する（yakkan S6。F1 は要素を落とすと precision が上がって跳ねる）。

## 4. 予測に使う語彙（差分）

基底仕様 §3（kind の一覧・cells の要否・図の種別ごとのノード粒度・timeline のエッジ 3 系統）を
そのまま継承し、次を追加する。**採点は完全一致なので、ここに書いていない語彙は当てようがない**
（yakkan W5：語彙未記載だけで kind 正解率 0.0 になった実例）。

**配る「予測の実例」は `docsynth eval --oracle --dump-pred` で正解から出す。**
手で書いた実例は仕様と食い違う（keiyaku V-E：配った実例が項番号を落としていた）。

### 4.1 `outline[].kind` / `elements[].kind` の追加語彙

| 紙面 | kind |
|---|---|
| 契約書・規約・法令の前文 | `preamble` |
| 頭書（冒頭の当事者・目的物・金額の一覧） | `head_matter` |
| 後文＋記名押印欄 | `signature` |
| 「別紙１」「様式第1号」 | `schedule` |
| 「附　則」 | `supplement` |
| 逐条解説の枠 | `commentary` |
| 「第一条」（漢数字の条） | `article`（数字の表記は kind に影響しない） |
| 法令の「一 二 三」の号 | `item`（「イ ロ ハ」は `subitem`） |
| 改定・改正履歴の表 | `table`（`semantic_type: history`） |

### 4.2 citation の書式

基底仕様どおり「紙面の番号だけを連ねた文字列」。**run-in ラベルは含めない**（§3-6）。ファミリーごとの例：

| family | 例 |
|---|---|
| contract | `第4条 2 (1)`（条は通し番号なので章を冠さない）。様式型（`employment`）は `1 (1) (ア)`（条が無い） |
| terms（web-numbered） | `3. (2)` |
| regulations | `第2章 第7条 2` |
| statute | `第二章 第五条 ２ 三 イ`（漢数字は**紙面の表記のまま**。採点側が正規化する） |
| insurance | yakkan と同一 |

### 4.3 当事者・記名押印欄

- 本文中の「甲」「乙」は**紙面の文字どおり**書き起こす（`{party:}` は生成側の機構であり、
  読み取り側は解決後の文字列を出す）。
- 記名押印欄の各行（住所・名称・代表者・「印」・収入印紙・契約日）は `pages[].text` に**入れる**が、
  **構造位置の採点対象ではない**（§5）。後文（「本契約の成立を証するため…」）は本文の段落なので**採点される**。

### 4.4 頭書・記入欄の表

頭書は**キャプションを持たない**表の連なり、または番号付き項目の羅列である。
表として出す場合は `semantic_type: head_matter`、様式型の記入欄は `form_fields`。
選択欄の記号は `■`（選択）/`□`（未選択）を**セルのテキストとして**書き起こす（画像判定を求めない）。

### 4.5 `pages[].text` に何を入れるか

紙面に印字されている文字は**順序どおりすべて**入れる（ヘッダ・フッタ・ページ番号は除く——
`layout.pages[].header/footer` 側の正解）。目次のリーダー罫は**点線なので文字が無い**
（`leader('.')` を禁止しているのはこのため。yakkan W6）。

### 4.6 図のノードの粒度（種別ごと）

基底仕様のとおり。`steps` のノードは「1 ステップ＝1 ノード」で、ステップ内の補足行は含めない
（keiyaku V-D で迷われた）。`timeline` のエッジは 3 系統（順序・期間・条件）。

## 5. どの要素が採点されるか（**出す／出さないで点が動くのはどれか**）

keiyaku の盲検読み取りで、読み手が最も迷ったのがここである（`../contracts/docs/evaluation.md` §4.9）。
**3 つの層を混同しない。**

| 層 | 対象 | 出さないとどうなるか |
|---|---|---|
| ① 構造位置の採点（coverage・citation 正解率・種別正解率） | **本文の項・号**（gold が `paragraph`/`item`/`subitem`/`subsubitem` の `label` を持つもの）。**前文の段落・後文・頭書の中の「記載の行」・別紙の項**も含む | 母数から外れる＝その分だけ取りこぼしになる |
| ② bbox（IoU・当たり率） | ①より広い——`derived.plain_text` に入るものすべて。**表のセル・図のノードラベル・条見出しの title・表題の文言・逐条解説の段落**を含む | 母数から外れるだけ（precision は下がらない） |
| ③ ページ本文（CER） | `pages[].text`。**紙面に出る文字は全部**（記名押印欄・頭書の項目名・奥付も） | ページ全体の文字列で測るので**点が下がる** |

**①の対象外**（出しても出さなくても構造位置の点は動かない）：
条・章見出しの**番号つきの行**（「第1条（目的）」。title だけの要素が gold にある）／表題・図題の
番号つきの行／表のセル（構造は `tables[].grid` と `cells` で採点。**bbox では採点される**）／
当事者表示と記名押印欄の各行／奥付／頭書の**項目名**（その下の記載の行は①の対象）。

## 6. ファミリー別の観点の効き方（バッチ設計・報告の指針）

全ファミリーで同じ指標を計算するが、文書の性質により母数が偏る。報告は
**ファミリー別（contract は骨格類型別）＋全体**で出し、母数が小さい観点は件数を併記する。
**母数が 3 content 未満の観点はデータカードが自動で申告する**（`docs/data_card.md` §4.3）。

| family / 類型 | 厚い観点 | 薄い観点 |
|---|---|---|
| contract 条文型（nda / outsourcing / delegation / consulting） | 構造位置（通し条番号）、当事者文字列、列挙、記名欄の bbox | 表（1〜3 点）、図（1 点） |
| contract 頭書型（lease / purchase の variant） | **表の意味座標**（頭書・分担表）、本文と表の値の対応、読み順 | 図 |
| contract 目録型（purchase / license） | 表 TEDS・セル F1、数値の抽出 | outline の深さ |
| contract 様式型（employment） | **表セル F1**、bbox、選択欄の読み取り | outline（浅い。条が無い）、参照関係 |
| contract 長文型（contracting / sysdev） | 深い outline、目次のページ一致、ヘッダ章名、読み順、漢数字の条 | — |
| terms | 深い入れ子リスト（列挙）、改定履歴表 | 図 |
| regulations | 章-条-項の outline、別表（wage_table）、改正履歴 | — |
| statute | 深い outline（編〜イロハ）、漢数字の正規化、目次の条範囲、別表の関係条 | 図（flowchart 1 点程度） |
| insurance | 全観点（yakkan と同一） | — |

**同名の条（「目的」「定義」「協議」「合意管轄」）がファミリーを横断して大量に現れる**ため、
`scoped` / `filtered` クエリの弁別評価は単一ドメインより厳しくなる＝**評価として良質になる**。
コーパスへの混入単位は「content ごとに 1 スタイル」を維持する。

## 7. 検索評価セット（**クエリ 10 種**。yakkan の全面改修を継承）

yakkan の実測で、旧 4 系統（term / heading / scoped / qa）には 2 つの欠陥があった：
(a) **gold パッセージの `title` を字面ごとコピーしていた**ため、素朴な文字 2-gram BM25 で nDCG@1 が 0.92 に
飽和し**順位の良し悪しを測る分解能が無い**、(b) 「被保険者」のような頻出語では**どの文書を返すべきかが
クエリから決まらない**。さらに `qa` の gold が 76% 誤った文書を指していた。
改修（2026-10-04 完了）の柱は 3 つ——**出現文書数（df）で振り分ける**・**gold の字面をコピーしない
クエリ系統を足す**・**紛らわしい非適合を明示する**。

| kind | 作り方 | 主指標 | 設計意図 |
|---|---|---|---|
| `term` | 定義語そのもの。**`df_docs == 1`（その語を定義する文書が 1 つ）に限る** | nDCG@1 | well-posed な項目検索。**飽和する前提**で「弁別力なし」の印を付けて配る |
| `heading` | 見出し語。同じく `df_docs == 1` に限る | nDCG@1 | 同上 |
| `scoped` | 文書名＋見出し名。**1 文書に同名の条が複数あるときは全部を grade 2 にして 1 クエリにまとめる** | nDCG@5 | 文書の特定が要る検索 |
| `filtered` | 見出し語＋`filters`（issuer / 商品名 / family / doctype）。**クエリ文に固有名を入れない** | nDCG@5 | メタデータ索引・ハイブリッド絞り込み |
| `enumeration` | 「◯◯を定義している箇所をすべて挙げよ」。**grade 1 を作らない**（打ち切りの問題が消える） | **Recall@100・r_precision** | 網羅要求 |
| `qa` | 自動 QA・執筆 QA の問いを流用。gold は出題元文書のパッセージ | nDCG@5 | 自然文の問い |
| `definition_masked` | **その語を使っている条文を文脈として与え、語を隠して定義を引かせる**（定義本文から語を隠すだけでは循環が断てず nDCG@1 0.94 だった） | nDCG@5 | 字面一致で解けない検索 |
| `multi_hop` | 「A 条が参照する B（別紙・表）」を 2 ホップで辿らせる | nDCG@5 | 参照関係の利用 |
| `situational` | 執筆 QA の **`apply` 型から機械的に昇格**（場面を与えて規定を当てはめる） | nDCG@5 | 実務的な場面検索 |
| `no_answer` | コーパスに答えが無い問い。**gold は空** | **`false_positive_rate`** | 「無い」と言えるか |

### 7.1 生成時の自己検査（V-S1〜V-S9。`export` の中で必ず走らせる）

**目視でも全数検査でもなく、生成時の検査が設計の穴を見つけた**（yakkan）。無効化しない。

| # | 検査 |
|---|---|
| V-S1 | `qa` の grade 2 は出題元 `doc_id` のパッセージである |
| V-S2 | 素の `term` / `heading` は `df_docs == 1` である |
| V-S3 | `enumeration` に grade 1 が無い（＝打ち切りが起きない） |
| V-S4 | **同一 kind・同一文字列のクエリが gold を食い違わせていない**（`filters` も見て判定する） |
| V-S5 | `definition_masked` のクエリと gold の字面重複が閾値（文字 2-gram で 0.5）以下 |
| V-S6 | クエリ文に番号ラベル（丸数字・`第N条`）が無い |
| V-S7 | `filters` が指す facet がコーパスで一意に 1 文書を決める |
| V-S8 | `definition` パッセージの `pages` が非空 |
| V-S9 | grade 1 の `term_id` がその文書でその語に割り当てられている（**`term_id` は文書をまたいで一意でない**） |

### 7.2 弁別力の申告

**素朴な検索器 3 系統**（B1 `title` 一致・B2 文字 2-gram BM25・B3 unigram TF-IDF）で全 kind を採点し、
`dataset/README.md` とデータカードに実測値を載せる。**系統間のスプレッドが小さい kind には
「弁別力なし（飽和）」の印を付けて配る**（yakkan では `term` だけがそうなった）。
意味で引く 3 kind（`definition_masked` / `multi_hop` / `situational`）が 0.3〜0.4 に収まっていれば、
字面一致では解けない＝順位を測れる状態である。

## 8. 何をもって「評価データとして使える」とするか（DoD。P7〜P8 で判定）

姉妹 2 本が到達した水準を合格ラインとして継承する：

1. `docsynth eval --all --oracle` が**全文書・全指標で満点**。
   **ただしこれは「ハーネスの自己整合」しか言えない**（正解から作った予測を正解で採点している）。
   正解そのものの妥当性は 3〜5 で確かめる。
2. `--misread` で崩すと全指標が recall 基準で単調に悪化（テストで固定）。
   **図が 3 点以上ある文書**で測る（1 点しかない文書では図の指標が動かない）。
3. **PDF だけを読む規則ベースの読み取り器**（`scripts/baseline_reader.py`）で全文書を採点でき、
   点が 0 と 1 の間で動き、文書の性質（ファミリー・骨格類型・style）で差が出る。
4. **構築文脈を持たない読み手による盲検読み取り**（`docs/validation_plan.md` §4）を
   **ファミリーごとに 1 本以上**（contract は骨格類型ごとに 1 本以上）通し、発見された契約の穴を
   すべて解消済み。**点が高いことは「契約が十分」を意味しない**——読み手が報告した
   「仕様に書いていない」をすべて docs に落としたことが条件（keiyaku で 28 件）。
5. 検索評価セットが V-S1〜V-S9 を通り、弁別力の実測（§7.2）が申告されている。
6. `manifest check`・`datacard check` が実ファイルと一致。`make check` 緑。
