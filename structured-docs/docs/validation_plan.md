## 0. 検証の階段（弱い読み手 → 強い読み手 → 文脈を持たない読み手 → 人間）

| 段 | 読み手 | 何が分かるか | 姉妹での発見例 |
|---|---|---|---|
| V-A | oracle（正解から作った満点の予測） | ハーネスの自己整合。**全文書・全指標で満点**になること | 見出し突合の取り違え（page_acc 0.39）→ 出現回数キーで修正（yakkan） |
| V-B | misread（崩した満点） | 指標が誤りに反応するか。**崩しの強さに対する単調性**（recall 基準） | 乱数の引き方を rate に依存させると単調性が壊れる（yakkan） |
| V-C | 規則ベースの読み取り器（`doc.pdf` だけを読む） | 内部 id を持たない外部予測を採点できるか＝**契約の穴** | outline に紙面に出ない節点 13.9%／列挙の番号規約が未定義（yakkan）。列挙の採点が citation 一致に依存し**完全に読めていても 0**／同じ citation に複数当たると coverage が 1 を超える（keiyaku） |
| V-D | VLM（このセッション自身がページ画像を読む） | 画像経由の読み取りに対して指標が意味を持つか | 目次リーダー罫の「.」約 2,800 字が CER を破壊／予測語彙の未文書化で kind 正解率 0.0（yakkan）。図ノードの `id` 必須で全ノードが 1 件に潰れる／**約款型の citation が二重**（keiyaku） |
| V-E | **盲検読み取り**（構築経緯を継承しない独立エージェント） | **内部構造を知らない読み手**が文書化された契約だけで採点まで到達できるか | 列挙表の caption 矛盾（lint L18 の新設）（yakkan）。配った実例が仕様と食い違う／「要素に出すか」「ページ本文に入れるか」「bbox で採点されるか」が混在（§4.9 の新設）／表を**位置**で対応づけていたため余分な表 1 つで TEDS 0.36／番号を持つ表を「下表」と呼ぶ箇所が 32 件（**L26 の新設**）（keiyaku） |
| V-F | 人間（HITL） | 機械では原理的に確認できないこと（§5） | 架空性・転載・版面の「それらしさ」・`apply` QA の算出値 |

各段は前の段が緑になってから進む。**「レンダリング成功」「lint 通過」「verify 通過」を根拠に段を飛ばさない。**

**点が出なかった観点は、ほぼすべて「読み取り側の力不足」ではなく「正解データ側」か「契約（仕様）側」の
問題だった**（keiyaku の実績）。V-C 以降で点が低い観点を見たら、まず自分の仕様を疑う。

## 1. V-A / V-B 自己評価（フェーズごとに常時）

- `docsynth eval --all --oracle` を `make check` の後に回す。1 指標でも満点を割ったら
  **採点側のバグ**として扱う（正解データを疑うのはその後）。
- `--misread` の単調性テストは**図が 3 点以上ある文書**で回す（契約書・規約・法令は図が 1〜2 点しか
  ないため、yakkan の「図 5 本以上」は満たせない。keiyaku は図 3 点＝ノード 24・辺 24・経路 9 の文書で
  単調性を固定できた）。単調性検査用に図を多めに持つ content を各ファミリーに 1 本用意する。
- **単調性は F1 ではなく recall で見る**（要素を落とすと precision が上がり F1 が跳ねる）。
- 検索評価セットは生成時に **V-S1〜V-S9**（`docs/evaluation.md` §7.1）を通す。

## 2. V-C 規則ベースの読み取り器（P7 の入口）

`scripts/baseline_reader.py` を移植し、新ファミリーの版面（無ヘッダの契約書・深い入れ子リスト・
漢数字見出し・条を持たない様式型）に対応する正規表現を足す。**読み取り器を作り込むのは目的ではない**——
入力は `doc.pdf` だけ、正解ファイルは開かない、限界は docstring に書く。

見るもの：全文書で採点が完走すること／指標が 0 と 1 の間で動くこと／
「読み取り器の力不足」と「契約の穴」を切り分けて後者を残らず潰すこと。

参考実測（keiyaku・契約書 41 文書）：CER 0.028・見出し F1 0.257・citation 0.774・TEDS 0.583・
列挙 0.680・読み順 1.000。**見出し F1 が低いのは読み取り器の力不足**（条見出しの体裁差）で、
契約の穴ではないと切り分けている。

## 3. V-D VLM 読み取り（P7〜P8）

ファミリーごとに 1 文書（contract は骨格類型ごとに 1 文書）、`pages/*.png` を**画像として**読み、
正解ファイルを開かずに予測 JSON を作って採点する。**外部 API は使わない**（このセッション自身が VLM。
商用サービスへの送信は `HITL_TODO.md` D4）。対象は版面の多様性を最大化して選ぶ。

チェック観点：`cells`（表の意味座標）と `bbox` も必ず出す（出さないとその指標が
「出せないのか出し方が未定義なのか」切り分けられない——yakkan X1）。

## 4. V-E 盲検読み取り（P8 の中心）

**構築経緯を一切継承しない新規サブエージェント**（fork ではない素の Agent）に、次だけを渡す：

- `dataset/<doc_id>/pages/*.png`
- `docs/evaluation.md`（予測 JSON の形・語彙・**§5 どの要素が採点されるか**）＋ `schema/prediction.schema.json`
- 形式の実例 1 本（**別文書**の予測 JSON。**`eval --oracle --dump-pred` で正解から出したもの**——
  手で書いた実例は仕様と食い違う。keiyaku V-E）
- **禁止**：`content/`、対象文書の `source.json` / `layout.json` / `answer.json` / `qa.json`

ファミリーごとに 1 本以上・版面はなるべく重ねない。**開発セッション自身による読み取り（V-D）では
踏まない欠陥が、盲検でだけ出る**（yakkan Z1：3 本中 2 本で契約の穴を発見。自読 3 本では一度も踏まなかった）。
発見した欠陥は lint / docs / 採点側の修正まで落とし切る。

**点が高いことは「契約が十分」を意味しない。** keiyaku の盲検 5 本は CER 0.000〜0.008 と高得点だったが、
同時に「仕様に書いていない」を合計 28 件報告しており、点が出たのは**正しく推測できたから**である。
報告された 28 件はすべて docs に明記して閉じた。**報告の件数が 0 になるまで続ける**。

### 5.1 `apply` 型 QA の確定手順（keiyaku H5 の手順を継承）

1. **機械検算**：問いの前提を形式仕様に落とし、別プロジェクト（正解プログラム。本体を書き換えない）で
   算出値を再計算する。一致／読み幅あり／不一致に分類する。
2. **読み幅の明示**：複数の読みが成立する問いを列挙し、採った読みとその理由を書き出す
   （自動生成のレビュー資料にする）。
3. **人間の承認**：読み幅のある問いだけを人間が承認する。不一致があれば答えを直す。
   承認後に `apply` を足すときも同じ手順を踏む。

keiyaku の実績：47 問を検算して一致 32・読み幅あり 15・**不一致 0**。読み幅 15 問を人間が承認し、
答えの修正は発生しなかった。回帰テストとして検算を固定している。

## 6. 恒常の安全網（フェーズを問わず無効化しない）

| 検査 | 守っているもの |
|---|---|
| render の内容欠落検出（全要素 ≥1 fragment、`_assert_nothing_dropped`） | **WeasyPrint は段またぎ要素で以降の内容を黙って捨てる**。「レンダリング成功≠内容が全部載った」 |
| verify V03（テキスト往復一致） | 版面の外に描かれた fragment・見た目変更の副作用（リーダー罫→border-bottom で脚注が消えた実例） |
| verify V04/V05（目次一致・描画漏れ） | span-all 表が後続を丸ごと消す事故。**目次が無い文書ではスキップした旨を明記**（黙って通さない） |
| **verify V11（結合セルがページ境界をまたがない）** | またぐと継続ページの列が空欄になり、**正解データのほうが誤りになる**（keiyaku の実害） |
| verify V-P1 / V-P5（記名欄と `meta.parties` の一致・`{party:}` の解決結果が紙面に出る） | 当事者の取り違え・トークンの未解決 |
| `manifest check`（`make check` 内） | 再生成後の更新忘れ（yakkan で checksum 差分 19 件が実際に残っていた） |
| **`datacard check`（`make check` 内）** | 文書を足してカードを更新し忘れること。**統計値の焼き込み**（両姉妹で事故あり） |
| **検索評価セットの自己検査 V-S1〜V-S9** | gold の字面コピーによる飽和・gold の誤配（yakkan で 76%）・同一文字列クエリの gold 食い違い |
| lint L16〜L26 | 「文章で書いた基準」を機械で強制する |
| 決定論テスト（同一入力 → 同一 `layout.json`・同一テキスト層） | 較正・キャッシュ・環境差の混入 |
