# style_guide.md — コンテンツ生成（執筆）ガイド

> 執筆・`families/<f>/library/`・QA 作成の作業では、**着手前に必ず本ファイルと
> `docs/authoring_checklist.md`、対象ファミリーの `families/<f>/docs/style.md` を読む**こと。
> `docs/authoring_checklist.md` は**lint が通っても残る欠陥の実例集**（転載の指紋・gold の誤り・
> 表と条文の空振り・定数の衝突・当事者の取り違えほか。姉妹 2 本で 150 content を書いて得た教訓）。
> 執筆プロトコル（scaffold → 執筆 → lint → fill_records → build → render → verify → review → qa）は
> CLAUDE.md §7。

## 1. 役割分担（yakkan-synth と同じ）

- **Python**：骨組み（scaffold）、番号・参照・目次・当事者呼称の導出、lint、描画、検証、自動 QA。
- **Claude**：条文本文、定義、表の中身、図のノード・エッジ、脚注・注記、alt/facts、執筆 QA。
- 執筆者（Claude）が**書いてはいけないもの**：番号ラベル（「第1条」「(1)」「①」「第二条」「イ」）、
  当事者呼称の直書き（「甲」→ `{party:client}`）、表・図番号の直書き（「表２」→ `{ref:tbl_x}`）、
  別紙・別表・様式番号の直書き、**位置で指す言い方**（「下表」「次の図」→ `{ref:}`。L26）、
  **Markdown 記法**（`**` `__` `` ` ``。そのまま紙面に印字される。L25。強調は `{b:}` `{u:}`）、
  `derived`、目次、ページ番号。すべて build が導出する。
- 書き直して**使わなくなった `parts/*.json` を残さない**（L24。誰にも見えない未執筆が残る）。
- 表・列挙表・条の組み立ては `scripts/authoring.py`（yakkan から移植）を使う。
  **ヘルパは検証しない**——書いたら必ず `docsynth lint` を通す。

## 2. 架空化ルール（全ファミリー共通・lint L08/L19 で強制）

| 対象 | 規則 |
|---|---|
| 会社名・サービス名・商品名 | 架空。実在名は denylist で検出。実在名の「もじり」（1字違い等）も禁止 |
| 法令の題名・自治体名（statute） | 架空。実在法令名・実在自治体名は denylist で検出（`docs/families.md` §6） |
| 人物名（代表者・担当者） | 架空。実在の著名人と同姓同名を避ける |
| 住所 | 架空の町名・番地（「東京都千代田区丸窓町一丁目1番1号」のように実在しない町名を使う）。都道府県・市区は実在可 |
| URL / メール | `example.jp` `example.co.jp` `example.com` のみ |
| 電話番号 | ゼロ埋めのみ（`0120-000-000` `03-0000-0000`） |
| 法令・裁判所への言及 | 実在の**名称のみ**可（「民法」「個人情報の保護に関する法律」「東京地方裁判所」）。法令の条番号は書かない（CLAUDE.md §15） |
| 金額・日付・期間 | 架空だが文書内で一貫（`meta.constants` ＋ `{const:}`、L11）。**同一値の使い回しは 2 概念まで**・実在商品/制度の代表値を避ける（yakkan checklist §4） |
| 様式番号・契約書番号・公布番号 | 架空 |
| disclaimer | 文書末尾（colophon）に「本書は読み取り検証用に生成された架空の文書であり…」の定型文を必ず入れる。ページごとには入れない |

### 転載の指紋（最重要。機械では検出できない）

**模倣は「文章」より先に「数値の列」「列挙の順序」「別表特有の語形」に出る**（yakkan で
5 文書が同じ形で違反した実証）。別表の数値は必ず自分で作り直し（等差・等比にしない、
端数を混ぜる、段数を実物と変える）、列挙は順序を入れ替え語彙を 1 つ以上差し替える。
業界共通の定型（「〜をいいます。」「ただし、〜を除きます。」「〜しなければならない。」）は
問題にしない。書き終えたら列挙と別表を読み返し「実物で見た形か」を自問する。

## 3. ファミリー別の文体

各ファミリーの詳細（語彙集・定型句・悪い例）は `families/<f>/docs/style.md` に置く。ここは要点のみ。

### contract（常体・条文体）
- 「〜とする。」「〜しなければならない。」「〜することができる。」。敬体を混ぜない（L10）。
- 当事者は必ず `{party:}`。前文で `{party:client|full}` により導入し、以降は alias（甲/乙）で参照する。
- 但し書き・ただし書きの入れ子は 2 段まで。1 文が長くなるのは実物どおりで構わないが係り受けは明確に。
- 一般条項（協議・管轄・通知）は library の型を使い回してよいが、文言は文書ごとに変える（L15）。

### terms（敬体・ユーザー向け）
- 「〜ものとします。」「〜できるものとします。」「〜ご確認ください。」。運営者の自称は
  「当社」（定義語として `{term:}` 化する）。
- 禁止事項・免責の列挙は入れ子リストで書く（表にしない方が実物らしい）。
- 過度に平易な UX ライティング（「〜だよ」）にはしない。実在規約の硬めの敬体を保つ。

### regulations（常体・規程体）
- 「〜と定める。」「〜による。」「〜ものとする。」。主語は「会社」「従業員」。
- 条見出しは体言（「（目的）」「（適用範囲）」）。総則 → 実体規定 → 雑則 → 附則の順。

### statute（常体・法令体）
- 「〜とする。」「〜してはならない。」「〜することができる。」「〜と認めるときは」。
  主語は「都道府県知事」「市長」「事業者」等の架空の役割名（役職は実在の一般名で可）。
- 定義は「この法律（条例）において『〇〇』とは、…をいう。」。号の列挙は名詞止めも可。
- 「及び／並びに」「又は／若しくは」の法令用法を正しく使い分ける（誤用は実物らしさを壊す）。
- みなし規定「〜とみなす」、準用「〜について準用する。この場合において、…と読み替えるものとする」
  を必須要素の範囲で使う。読替えは読替え表（reading_replacement）にしてもよい。
- 罰則は「〜した者は、…以下の拘禁刑又は…以下の罰金に処する」型（条例は過料）。
  **量刑の数値は実在法令の代表値を写さない**（§2 の指紋）。

### insurance
- yakkan-synth の `../insurance-contracts/docs/style_guide.md` のとおり（移植ファミリーのため変更しない）。

## 4. 本物らしさの密度要件

- 読者が斜め読みして「テンプレを埋めただけ」と感じる文書は不合格。各条に具体的な数値・期間・
  手続き・例外が入っていること（例：NDA なら「開示後 3 年間」「書面による事前承諾」「複製の範囲」）。
- 定義語は定義して**使う**（L12 は未定義使用しか拾わない。死語は自分で消す）。
  同じ語を 2 か所で違う内容に定義しない。章ごとに呼称を変えない（`{term:}` に統一）。
- 表・図は本文と噛み合っていること：本文が「別紙１に定める」と言ったら別紙１が実在し（L01）、
  表の値が本文の数値と一致する（L11）。**一覧表が掲げる項目には必ず対応する条文を置く**
  （逆も然り。yakkan checklist §5）。
- 表・図は**導入文を持つ項の blocks** に入れる（条直下に置くと導入文より前に描画され、
  読み順・アンカーの QA が壊れる。yakkan checklist §3）。
- `{ref:}` は参照先の**存在**しか lint されない。**意味が合っているか**（指した項に本当に
  その規定があるか）は執筆者と reviewer が見る（yakkan checklist §8）。
- 図の `alt` / `facts` は QA の正解そのもの。「◯◯は四つに分かれる」と書いたら本文を数えて確かめる。
  図・算式の数値は必ず `{const:}` で書く（生文字列は定数変更に追従しない）。
- 参照表（definitions / fee_schedule / wage_table / …）には `records` を付ける
  （`scripts/fill_records.py`。結合セルのある表は手で書く）。
- 同一 doctype の複数文書では、題材（業種・目的物・サービス種別）、当事者、章構成、数値を変える。
  `lint --similarity`（文単位重複 30% 超で警告）を執筆完了ごとに実行する。

## 5. QA 執筆（1 文書 15 問。L16 が配分を強制）

- 種別は基底仕様の 11 種。**表の問い（table_lookup＋table_reason）3 問以上・
  図の問い（figure_path＋figure_fact）3 問以上・apply 1 問以上・件数ちょうど 15**（family.yaml で変更可）。
- 型の選び方（yakkan checklist の表を継承）：

| 問いの形 | 型 |
|---|---|
| 本文・表から**そのまま**引ける | `extract` `table_lookup` `definition`（answer が evidence の平文に含まれることを L14 が検査） |
| 表の中で**比べる** | `table_reason` |
| 場面を与えて**規定を当てはめ、値・結論を導く** | `apply`（包含検査対象外。**執筆 QA でしか作れない**） |
| 図の経路・隣接／記述の真偽 | `figure_path`（答えは図に実在するラベル）／`figure_fact` |
| 参照先／数／存在しないもの／ページ | `crossref`／`count`／`negative`／`locate` |

- `apply` の例：「業務委託契約で、乙が 2026 年 5 月 10 日に納品し甲の検査期間が 10 営業日の
  場合、検収の期限はいつか」「第◯条の届出を怠った事業者に科されるのはどれか」。
- **`apply` の答えは「機械検算 → 読み幅の明示 → 人間の承認」で確定させる**
  （`docs/validation_plan.md` §5.1）。L14 の包含検査にも eval にも引っかからないので、
  自分で計算したまま置かない。**前提（起算日・営業日の数え方・端数処理）を書き出しておく。**
- `apply` 型は検索評価セットの `situational` クエリに機械昇格される（`docs/evaluation.md` §7）。
  **場面の記述を具体的に書くと検索クエリとしても質が上がる。**
- `evidence` は必ず存在する要素 id を指す（L14）。**答えは evidence 1 つの平文に収まる形**に書く
  （2 セルにまたがる答えは L14 で落ちる。しかも `lint` では通り `qa` で初めて落ちる）。
  書いたら `docsynth qa --validate` を通す。

## 6. 執筆チェックリスト（review 時に全ページ PNG を見ながら）

**全文は `docs/authoring_checklist.md`**（16 節）。ここには版面を見ながら確かめる項目だけを置く：

1. 当事者の取り違え（甲がすべき義務が乙になっていないか）。`{party:}` を使っていても
   **論理の取り違え**は lint で検出できない。条ごとに主語を確認する。
2. 記名押印欄：当事者表示・前文・署名欄の名称/住所が一致して**描画されている**か（L19 は JSON を見るが、
   目視で紙面も確認する）。
3. 改定履歴の日付が effective_date・本文中の日付と矛盾していないか。
4. 入れ子リストのインデントが崩れていないか（3 階層目のぶら下げ）。
5. 契約書らしくないページ割れ（後文と署名欄の分離、条見出しだけがページ末尾に残る）がないか。
6. statute：漢数字ラベルの欄からのはみ出し、目次の条範囲と実際の条の一致（verify も見るが目視でも）、
   「及び/並びに」等の用法。
7. disclaimer が末尾にあるか。本文中に「架空」の断り書きが漏れ出していないか。

新たに見つけた「lint が通っても残る欠陥」は **`docs/authoring_checklist.md`** に追記する
（2 回同じ指摘を受けたら必ず）。**機械化できるものは lint / verify に落とす**（新設は L27 以降）。

## 7. 描画で踏む罠（内容の問題ではない。基底 checklist から要点のみ）

- `RenderLayoutError` は内容の高さが特定の「帯」（実測 48 字幅）に一致したときだけ起きる。
  対処の順序：(1) 字数を帯の幅以上増減、(2) 項の分け方を変える、(3) 別の style で描く。
  自分の文が悪いと思って探索しすぎない。
- 段組の中で `span_columns: true` を使わない。横長の表は列数を減らすか見出し語を短くする。
- **「レンダリングが成功した」は「内容が全部載った」を意味しない。** 必ず verify を見る。
- 「fragment はあるのに PDF にテキストが無い」ときは bbox が版面の外に出ていないか見る。
