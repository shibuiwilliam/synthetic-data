# authoring_checklist.md — 執筆前・執筆後に必ず確認すること（全ファミリー共通）

> **新しい content を書くときは、着手前にこの全文を読むこと。**
> `docs/style_guide.md`（文体・架空化）と `docs/schema.md`（型）を置き換えるものではなく、
> **「lint が通っても残る欠陥」を潰すための追加チェックリスト**である。
> 基底：`../insurance-contracts/docs/authoring_checklist.md`（約款 100 content の教訓）＋
> `../contracts/docs/authoring_checklist.md`（契約書 50 content の教訓）。
> **新たに見つけた欠陥はこのファイルに追記する（2 回同じ指摘を受けたら必ず）。**
> 機械化できるものは lint / verify に落とす（新設は L27 以降。`docs/lint_rules.md`）。
>
> - 版: 1.0（2026-10-05 新設）

---

## 1. 転載 — いちばん重い違反（lint は検出できない）

**模倣は文章より先に「数値の列」「列挙の順序」「別表特有の語形」に出る。** yakkan では
**5 文書で同じ形の違反が再発した**。危険なのは 5 つ：**条・章の並び順／列挙の順序と語彙／
別表・目録の数値の列／様式の項目の並び／表記の癖**（`docs/style_guide.md` §2.1）。

- **別表・目録・賃金表の数値は必ず自分で作り直す。** 等差・等比にしない（作り物に見える）。
  端数を混ぜ、段数・区分を実物と変える。
- **列挙は順序を入れ替え、語彙を 1 つ以上差し替える。**
- 「特定のひな型でしか見ない言い回し」を使わない。業界共通の定型（「〜をいう。」
  「ただし、〜を除く。」「本契約の成立を証するため」「〜しなければならない。」）は問題にしない。
- **判定軸ごと変える**のがいちばん確実（負担区分表の軸を「部位別」から「原因別」に変える 等）。
- **statute 固有**：法令の条文は著作権の対象外だが同じ規約で扱う。**特定の実在法令に固有の
  定義列挙・数値基準（量刑・期限・面積）・別表の構成を写さない**。「〜の許可を受けなければならない」級の
  法令定型句は許容する。
- **書き終えたら、条の並び・列挙・別表を読み返して「実物で見た形か」と自問する。
  見覚えがあるなら、それが模倣の証拠。**

## 2. 正解データ（gold）自体の誤り

`facts` と `alt` は **QA の正解そのもの**。間違っていると評価が壊れる。

- 図の `facts` に「◯◯は四つに分かれる」と書いたら、**本文を数えて確かめる**
  （yakkan では「四つの節」と書いて 6 節だった実例がある）。
- 図のノードラベルと本文の見出しを一致させる。**図だけ短縮した名前にしない。**
- 図・算式の中でも `{const:}` `{term:}` `{ref:}` が使える。**数値は必ず `{const:}` で書く**
  （生文字列は定数変更に追従しない。yakkan では 4 文書で起きた）。
  太字・ルビ・改行・脚注は SVG に形が無いので L06 が弾く。

## 3. 表・図は「導入文を持つ項の `blocks`」に入れる（L22）

条（`article`）や章の直下に置くと**導入文より前に描画される**。「次のとおり」が 2 段落上の表を
指す状態になり、読み順・アンカーの QA が全滅する。`layout.json` の `pages[].reading_order` で確認できる。

## 4. 列挙の入れ子（L23）

同じ親の下に号の並びが 2 組以上あるなら、号は**それを導入する項の `children`** に入れる。
兄弟に平らに並べると「(1)〜(5) と (1)〜(3)」が「(1)〜(8)」になる。
**terms の 3 階層リスト・statute の「号 → イロハ → （１）」は特に踏みやすい。**

## 5. `meta.constants` の値を散らす

同じ値が複数の概念に使われていると数値 QA の弁別力が無くなる（yakkan では 30 日が 4 概念に使われていた）。

- 同一値の重複は**最大 2 件**まで。宣言しただけで使わない定数を残さない。
- 本文にハードコードした数値を残さない（`{const:}` を通さないと L11 が効かない）。
- **制度上の代表値を避ける**（下請法の 60 日、遅延損害金 14.6%、消費税率、法定利率、
  法定の労働時間・休暇日数、罰金の上限額）。実在制度を指す値は転載の指紋と同じ問題を持つ。

## 6. 当事者（contract で最も多い欠陥）

**`{party:}` を使っていても論理の取り違えは機械検出できない。** 条ごとに確認する。

- **義務の主体が逆になっていないか。** 受託者・委託者、貸主・借主、売主・買主、開示者・受領者は
  取り違えやすい。
- **権利と義務が片方に偏っていないか**（実物の契約書は双方に義務がある）。
- 前文で導入した当事者を**全員使っているか**。3 者契約では「丙」の役割が**条文に実質を持っているか**
  （記名欄にだけ出てくる当事者は不自然）。
- 記名押印欄の名称・住所・代表者が当事者表示・前文と一致しているか（L19 は JSON を見る。
  **紙面は目視で確認する**）。
- **単独名義の文書（terms / regulations / statute / insurance）では `issuer` の表記を揺らさない**
  （「当社」「本会社」「弊社」の混在。定義語として `{term:}` 化する）。

## 7. 中身の整合（実務・制度と矛盾させない）

法的助言ではなく「**読者が違和感を持たない程度の整合**」を目指す。

- contract：契約不適合責任の期間と検査・検収の期間を混同しない／所有権移転と危険負担の移転は別に定める／
  秘密保持の契約期間と義務の存続期間を書き分ける／再委託を禁止しておいて再委託先の義務を定めていないか／
  解除事由に挙げた事象が別の条で許容されていないか／損害賠償の上限を超える定めが他の条に無いか。
- terms：改定条項の手続き（通知の方法・効力発生時期）と改定履歴の日付が矛盾しないか／
  免責の範囲が「一切の責任を負わない」だけになっていないか（実物は例外を置く）。
- regulations：就業規則の労働時間・休憩・休暇が相互に矛盾しないか／懲戒事由と手続きの対応／
  附則の施行日と改正履歴の日付の整合。
- statute：**「及び／並びに」「又は／若しくは」の法令用法**を正しく使い分ける（誤用は実物らしさを壊す）／
  罰則の構成要件が義務規定と対応しているか／経過措置が施行日と矛盾しないか／
  準用・読替えの対象条が実在するか。
- 様式型：**選択肢の組み合わせが矛盾しないか**（「期間の定めなし」に契約期間が書かれている等）。

## 8. 表・別紙と条文の対応を空振りさせない

- 一覧表が掲げる項目には**必ず対応する条文を置く**（逆も然り。yakkan では一覧に 5 つ挙げて条文が 3 つの例）。
- 本文の「別紙1に定める」に対応する別紙が**実在し、中身が空でない**か（L01 は存在しか見ない）。
- 頭書の値（賃料・期間・敷金）が本文の `{const:}` と一致しているか。
- 別紙の合計値が本文の代金・委託料と一致しているか。
- **別紙・別表・様式の 3 系統を混ぜて使うときは、参照が正しい系統を指しているか**
  （「別紙1」と「別表1」は別物。`kind_label` ごとに番号が振られる）。
- statute：別表の「（第◯条関係）」が指す条に、その別表を参照する規定が実在するか。

## 9. `{ref:}` は「意味が合っているか」まで見る（L26 も併せて）

lint は参照先の**存在**しか見ない。

- 「…の取扱いは第3項のとおり」と書いて、実際は第4項にも書いてあった（yakkan の実例）。
- 「別紙に定める」と素の文字列で書き、別紙が 3 つあってどれか決まらなかった
  → **別紙・別表・様式への参照も必ず `{ref:}` で書く**。
- 前条・次条を「前条」と書きたくなるが、**`{ref:}` を使う**（build が「第4条（◯◯）」に解決する）。
- **「下表」「次の図」で指さない**（L26 が warn。版面が変われば嘘になる。1 content を複数 style で
  描くのが本プロジェクトの前提なので致命的）。

## 10. 定義語

- 定義した語は本文で**実際に使う**（L12 が拾うのは未定義使用と未使用定義だけ）。
- 同じ語を 2 か所で違う内容に定義しない。定義の基準語をそろえる
  （「本件業務」を定義して「委託業務」と書くと定義がカバーしない）。
- 章ごとに呼称を変えない（`{term:}` に統一）。
- **定義文が紙面のどこにも現れない**状態にしない（L12 が検査するが、定義表の行を削ったときに踏む）。

## 11. `records` を付ける

参照表（`definitions` / `fee_schedule` / `deliverables` / `inventory` / `head_matter` / `form_fields` /
`allocation` / `wage_table` / `rate` / `procedure` / `mapping` / `history` / `reading_replacement`）は
`grid` と `records` の二重表現を持つ。

```
uv run python scripts/fill_records.py content/<cid> --write
```

**結合セルのある表（頭書・負担区分表・記入欄・賃金表）は機械導出できないので手で書く。**
列挙表（`enumeration` / `exclusions`）は参照表ではないので不要（かつ caption を付けない。L18）。

## 12. QA を書くときの型の選び方

`extract` / `table_lookup` / `definition` は **answer が evidence の平文に含まれていること**が L14 で
検査される。**要約した答えや算出値を書くとエラーになる。**

| 問いの形 | 型 |
|---|---|
| 本文・表から**そのまま**引ける | `extract` `table_lookup` `definition` |
| 表の中で**比べる**（どちらが負担するか・最大） | `table_reason` |
| 場面を与えて**規定を当てはめ、値・結論を導く** | **`apply`**（包含検査の対象外。**自動生成できない唯一の型**） |
| 図の経路・隣接 | `figure_path`（答えは図に**実在するラベル**でなければ L14 が落とす） |
| 図の記述の真偽 | `figure_fact` |
| 参照先 / 数 / 存在しないもの / ページ | `crossref` / `count` / `negative` / `locate` |

- **`apply` の算出値は lint も eval も検査できない。** 「機械検算 → 読み幅の明示 → 人間の承認」の
  手順で確定させる（`docs/validation_plan.md` §5.1）。自分で計算し、前提を書き出しておく。
- 配分（既定 15 問・表 3・図 3・apply 1。contract は図 2・apply 2）は **L16 が error で強制する**
  ——文章で書いただけでは守られない（yakkan では 30 content のうち 13 が違反していた）。
- `apply` 型は検索評価セットの `situational` クエリに機械昇格される（`docs/evaluation.md` §7）。
  **場面の記述を具体的に書くと検索クエリとしても質が上がる。**

## 13. Markdown の名残と番号の直書き（L03・L25）

- 強調は `{b:}` `{u:}`。**`**` `__` `` ` `` は書かない**（そのまま紙面に印字される。keiyaku で実例）。
- 番号ラベル（「第1条」「(1)」「①」「第二条」「イ」）・当事者呼称（「甲」）・表図番号（「表2」）・
  別紙番号は**すべてトークン**で書く。
- `parts/*.json` を書き直して使わなくなったファイルを**残さない**（L24。誰にも見えない未執筆が残る）。

## 14. 描画で踏む罠（内容の問題ではない）

- **`RenderLayoutError`** は内容の高さが特定の「帯」（実測 48 字幅）に一致したときだけ起きる。
  対処の順序：(1) 字数を帯の幅以上増減、(2) 項の分け方を変える、(3) 別の style で描く。
  **自分の文が悪いと思って探索しすぎない。**
- **「レンダリングが成功した」は「内容が全部載った」を意味しない。** 必ず `verify` を見る。
- 横長の表（頭書・目録・工程表・賃金表）は列数を減らすか行見出しの語を短くする（A4 1 段で 15 列まで）。
- **結合セルをページ境界にまたがせない**（V11。またぐと正解データのほうが誤りになる）。
- 枠つきブロック（`commentary`・備考枠）が**ページ境界で割れると続きが版面の外に出る**ことがある。
  長い解説は複数ブロックに分ける。
- 2 段組の style では段またぎ要素（`span_columns`）を使わない。
- 「fragment はあるのに PDF にテキストが無い」ときは bbox が版面の外（マージン帯）に出ていないか見る。

## 15. 組み立てヘルパ `scripts/authoring.py`

parts の JSON を手で書くと、セルの id・`rowspan`・`records` を取り違えやすい。
`C` / `merged`（セル・結合に飲み込まれた位置）、`table`（見出し 1 行の表＋records）、
`enum_table`（文と一体の列挙表。番号欄は `{auto_label}`・**caption を付けない**）、
`art`（条・項・号・条末脚注）、`write`（UTF-8・indent 2・末尾改行）。

**ヘルパは検証しない。** 書いたら `docsynth lint content/<cid>` を必ず通す。

## 16. 仕上げの手順

```
uv run docsynth lint content/<cid>               # error 0 / warn 0 にする
uv run python scripts/fill_records.py content/<cid> --write
uv run docsynth build content/<cid>
uv run docsynth render content/<cid> --style <sid>
uv run docsynth verify dataset/<doc_id>          # error 0 / warn 0 にする
uv run docsynth qa dataset/<doc_id>              # 自動 QA ＋ 検証（執筆 QA の L14 はここで初めて通る）
uv run docsynth manifest update
uv run docsynth review dataset/<doc_id>          # 全ページ PNG を自分で開いて見る
```

**`docsynth qa` を `batch` の前に必ず挟む。** 執筆 QA の「answer が evidence の平文に含まれるか」（L14）は
`source` と `layout` が揃って初めて検査できるので、**`lint` では通ってしまう**
（keiyaku の実例：答えが 2 セルにまたがっていて batch で落ちた）。
答えは**evidence 1 つの平文に収まる形**に書く。

macOS では `DYLD_FALLBACK_LIBRARY_PATH=/opt/homebrew/lib` が要る（`make` 経由なら自動）。

**最後に PNG を全ページ自分で開いて見る。** ページ数と lint が通っても崩れていることはある
（yakkan：図の辺ラベルの重なりは verify では検出できず目視でのみ発覚）。
