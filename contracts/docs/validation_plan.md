# validation_plan.md — データセットの検証・硬化計画

> データセット v1 を「使える」と宣言する前に通す検証の計画。CLAUDE.md §12 の **P7** に対応する。
> yakkan-synth が 7 次にわたる残課題ループ（R/S/T/W/X/Y/Z・計 38 件。
> `../insurance-contracts/docs/remaining_issues.md`）で実際に欠陥を見つけた手順を、最初から計画に組み込む。
>
> **各段の目的は点を上げることではなく、欠陥を出させること。**
> 見つけた欠陥は `docs/decisions.md`（設計判断）と本ファイル §7（実施記録）に残し、可能なものは必ず
> lint / verify / テストに落とす（「文章で書いただけの基準は守られない」——yakkan では 30 content のうち
> 13 が執筆 QA 基準に違反していた）。

## 0. 検証の階段（弱い読み手 → 強い読み手 → 文脈を持たない読み手 → 人間）

| 段 | 読み手 | 何が分かるか | yakkan での発見例 |
|---|---|---|---|
| V-A | oracle（正解から作った満点の予測） | ハーネスの自己整合。**全文書・全指標で満点**になること | 見出し突合の取り違え（page_acc 0.39）→ 出現回数キーで修正 |
| V-B | misread（崩した満点） | 指標が誤りに反応するか。**崩しの強さに対する単調性**（recall 基準） | 乱数の引き方を rate に依存させると単調性が壊れる |
| V-C | 規則ベースの読み取り器（`doc.pdf` だけを読む） | 内部 id を持たない外部予測を採点できるか＝**契約の穴** | outline に紙面に出ない節点 13.9%／列挙の番号規約が未定義／全文一致だけの突合 |
| V-D | VLM（このセッション自身がページ画像を読む） | 画像経由の読み取りに対して指標が意味を持つか | 目次リーダー罫の「.」約 2,800 字が CER を破壊／予測語彙の未文書化で kind 正解率 0.0 |
| V-E | **盲検読み取り**（構築経緯を継承しない独立エージェント） | **内部構造を知らない読み手**が文書化された契約だけで採点まで到達できるか | 列挙表の caption 矛盾（lint L18 の新設）／timeline エッジ規則の記述不備 |
| V-F | 人間（HITL） | 機械では原理的に確認できないこと（§5） | 架空性・転載・版面の「それらしさ」・`apply` QA の算出値 |

各段は前の段が緑になってから進む。**「レンダリング成功」「lint 通過」「verify 通過」を根拠に段を飛ばさない。**

## 1. V-A / V-B 自己評価（フェーズごとに常時）

- `keiyaku eval --all --oracle` を `make check` の後に回す。1 指標でも満点を割ったら
  **採点側のバグ**として扱う（正解データを疑うのはその後）。
- `--misread` の単調性テストは**図が 3 本以上ある文書**で回す（契約書は図が 1〜2 点しかないため、
  yakkan のように「図 5 本以上」を満たす文書が無い。単調性検査用に図を多めに持つ content を
  1 本だけ作る——`sysdev` か `contracting` が向く）。
- **単調性は F1 ではなく recall で見る**（要素を落とすと precision が上がり F1 が跳ねる）。

## 2. V-C 規則ベースの読み取り器（P6 の入口）

`scripts/baseline_reader.py` を移植し、契約書の版面に対応する正規表現を足す：

- ヘッダの無いページ、`- 1 -` 型フッタ
- 「第N条（見出し）」の inline 見出し、無番号の第1項
- 「ア イ ウ」「(ｱ)」の細目
- 様式型の「1 項目名」「(1)」「①」（**条が無い**）
- 頭書の大型表・記入欄の表（罫線表からのセル抽出）
- 記名押印欄（「住所」「名称」「代表者」「印」の並び）

**読み取り器を作り込むのは目的ではない**——入力は `doc.pdf` だけ、正解ファイルは開かない、
限界は docstring に書く。見るもの：全文書で採点が完走すること／指標が 0 と 1 の間で動くこと／
**「読み取り器の力不足」と「契約の穴」を切り分けて後者を残らず潰すこと。**

### 実施の記録（2026-09-28・全 41 文書）

`uv run python scripts/baseline_reader.py dataset/<doc_id> -o <pred>` を 41 文書で回し、
`keiyaku eval --all --pred-dir` で採点した。**41 文書すべてで完走**（落ちたものは無い）。

| 指標 | 平均 | 読み |
|---|---|---|
| 本文 CER | 0.028 | 版面からの本文の取り出しはほぼ正しい |
| 見出し F1 | 0.257 | **骨格によって 0 と 0.44 に割れる**（下記） |
| 構造位置 citation 正解率 | 0.774 | 拾えた要素については位置づけが合う |
| 構造位置 カバー率 | 0.169 | 段落の切り方が違うと全文一致しない（`coverage_contains` は 0.68） |
| 表 TEDS | 0.583 | 罫線のある表は取れる。罫線の無い form の表は落ちる |
| 図ノード F1 | 0.454 | 箱の中の文字は取れる。エッジ・経路は 0（規則で追っていない） |
| 列挙の順番一致 | 0.680 | 中身での突合を入れた後（前は 0.560） |

**切り分けた結果**：

| 見つけたこと | 読み取り器の力不足 / 契約の穴 | 処置 |
|---|---|---|
| 様式型（`employment` 4 文書）は outline・citation・列挙がすべて 0 | 力不足（条が無い文書の見出しを拾う規則を持たない） | docstring の限界に追記 |
| 約款型（`contracting`）は見出しがほぼ 0（form で 0.000／mincho で 0.02） | 力不足（**条見出しが条番号の上**にあり、条番号の行に本文が続く） | 同上。漢数字の条番号は読めるようにした |
| 読み取り器が語彙に無い `kind: "caption"` を出し、採点側に弾かれていた | **契約の穴**（表題をどう出すかが未定義だった） | 当てられない種別は `null` で出す、と docstring に明記して修正 |
| 条番号を外すと、**列挙を完全に読めていても 0** | **契約の穴**（指標が測るものと突合の鍵がずれていた） | 中身での突合を追加（`docs/decisions.md` 119。H6 の承認済み変更） |
| 同じ citation に複数の予測が当たると **coverage が 1 を超える**（実測 1.67） | **契約の穴**（採点のバグ） | gold 1 件につき 1 回だけ数える |

## 3. V-D VLM 読み取り（P6〜P7）

**骨格類型ごとに 1 文書**（条文型・頭書型・様式型・長文型）、`pages/*.png` を**画像として**読み、
正解ファイルを開かずに予測 JSON を作って採点する（外部 API は使わない。このセッション自身が VLM）。

チェック観点：`cells`（表の意味座標）と `bbox` も**必ず出す**（出さないとその指標が
「出せないのか出し方が未定義なのか」を切り分けられない）。
契約書で特に見たいもの：**当事者呼称の解決**（「甲」が誰か）、**頭書と本文の対応**、
**チェックボックスの選択状態**、記名押印欄の要素分割。

### 実施の記録（2026-10-02・骨格類型ごとに 1 文書）

`pages/*.png` だけを読み（`source` / `layout` / `answer` / `qa` / `content/` は開かない）、
予測 JSON を書いて採点した。**契約の穴を直す前後**の両方を載せる。

**切り分け**——点が出なかった観点は、**3 つとも「契約の未記載」**で、読み取りの力不足ではなかった。

| 直す前 | 原因 | 直した後 | 処置 |
|---|---|---|---|
| 見出し F1 0.32 | `outline` に条だけを出した。gold は**項・号も**含む（73 件中、条は 13 件） | 0.99 | `docs/evaluation.md` §4.1 に明記 |
| CER 0.63 | 本文を先に並べ、見出しと表を後ろにまとめた。gold は**紙面の読み順** | **0.00** | §4.5 に表で明記（図の中の文字は入れない／奥付は入れる／柱とノンブルは入れない） |

| citation 正解率 0.72（約款型） | **正解データの欠陥**。条見出しを条の上に置く体裁で、条ラベルが第1項へ走り込むぶんを位置づけにも入れていた。号が「第三条 第三条 (1)」と**二重**になり、外からは再現できない | **1.00** | `citation` から `run_in_label` を外し、`dataset/` を再生成（decisions 123） |

**当事者呼称・頭書・チェックボックス・記名押印欄**（契約書で特に見たかった 4 点）は、
いずれも**そのまま採点できた**：

- 甲・乙は紙面の文字どおり書き起こせばよく、`qa` の `extract` で同定を問う設計で足りている。
- 頭書は `頭書 1` の citation で **citation 正解率 1.00・カバー率 1.00**（`pur-0002`）。
- チェックボックスは `■ 無し` をセルの文字として書き起こして **TEDS 1.00・セル F1 1.00**（`emp-0002`）。
- 記名押印欄は**記名行ごとに 1 要素**で bbox 当たり率 0.82（`pur-0002`）。「印」も本文に含めた。

**約款型（`con-0002`）で見つけた正解データの欠陥**：条見出しが条番号の上にある体裁の文書では、
号の citation に条番号が二重に入っていた（「第三条 第三条 (1)」）。**読み取り器の力不足ではなく、
外からは再現できない正解**だったので、生成側を直して `dataset/` を作り直した（decisions 123）。
漢数字の条番号（`第二十四条`）そのものは、紙面どおり書き起こせばそのまま突合できた。

**残る限界**（読み手側。直さない）：bbox は目分量なので当たり率 0.65〜0.98。
図の経路は、輪のある流れ図で gold が 2 本持つところを 1 本しか出せなかった（`pur-0002` 経路 F1 0.67）。

## 4. V-E 盲検読み取り（P7 の中心）

**構築経緯を一切継承しない新規サブエージェント**（fork ではない素の Agent）に、次だけを渡す：

- `dataset/<doc_id>/pages/*.png`
- `docs/evaluation.md`（予測 JSON の形・語彙）＋ `schema/prediction.schema.json`
- 形式の実例 1 本（**別文書**の予測 JSON）
- **禁止**：`content/`、対象文書の `source.json` / `layout.json` / `answer.json` / `qa.json`、
  `blueprints/`、`CLAUDE.md`

**骨格類型ごとに 1 本以上**・版面はなるべく重ねない。**開発セッション自身による読み取り（V-D）では
踏まない欠陥が、盲検でだけ出る**（yakkan：盲検 3 本中 2 本で契約の穴を発見。自読 3 本では 0 件）。
発見した欠陥は lint / docs / 採点側の修正まで**落とし切る**。

（うち一部は、この回の `下表 → 表N` の修正前に撮った画像を読んだことによる差）。
`sys-0001` の表は、**罫線で囲まれた当事者表示を表として 1 つ余分に出した**ために位置がずれて
TEDS 0.36 まで落ちた——採点側を「キャプション → 中身 → 位置」に直して **0.97** になった（decisions 129）。

**点はほぼ満点だったが、報告された「仕様に書いていない」は 1 巡目 16 件・2 巡目 12 件**あった。
点が出たのは**読み手が正しく推測できたから**であって、契約が十分だったからではない。
16 件すべてを gold の実測に合わせて `docs/evaluation.md` §4.8 に決めた（例：逐条解説の `citation` は空、
表題・条見出しの行は `elements` に出さない、奥付は出す、`timeline` のエッジは `next`/`from`/`to`/`at`、
`bbox` は 1 要素 1 矩形で左右は段の端、CER は正規化後）。

**あわせて見つかった配布物の欠陥**：形式の実例として配った予測 JSON（手書き）が `pages[].text` の
項番号を落としており、**仕様と実例が食い違って**いた。手書きの実例は規約からずれるので、
`keiyaku eval <doc> --oracle --dump-pred <path>` で**正解から満点の予測を書き出せる**ようにした
（`docs/decisions.md` 126）。

契約書で盲検が暴きそうな穴（仮説。**2026-10-02 に実施して検証した**）：

- `head_matter` の citation 表記が未定義（「頭書」と書くのか無しか）
  → **当たった**。当事者表示の 2 行を `head_matter` と読むか `paragraph` と読むかで割れた（§4.8 で `paragraph` に決定）
- 記名押印欄をどこまで 1 要素にするか（住所・名称・代表者・印の粒度）
  → **当たった**。2 本とも「記名行ごと 1 要素でよいか」を挙げた（§4.3 のとおりで正しかったが、印影の扱いが未記載だった）
- 様式型の `kind` 割当（「1」を `chapter` と当てられるか）→ 今回の 2 本は条文型なので未検証
- チェックボックスの記号をテキストに含めるか → 今回の 2 本には無い（V-D の `emp-0002` で検証済み）
- 別紙・別表・様式の 3 系統をどう区別して出すか
  → **当たった**。「別表1」を `別紙1` に正規化するのか紙面どおりかが未記載だった（§4.8 で紙面どおりに決定）

**商用外部サービス（OCR / VLM API）での検証は行わない**——2026-09-27 に H8 が「不可」で決定した
（`HITL_TODO.md`）。したがって V-C・V-D・V-E は**すべてこのリポジトリの中とこのセッションの中で完結する**。
外部の読み取り器で測りたくなったときは、まず H8 を起票し直すこと。

## 5. V-F HITL（人間の判断が要るもの）

`HITL_TODO.md` に **AI が代わりに下さない判断のうち、まだ決まっていないもの**だけを置く。
