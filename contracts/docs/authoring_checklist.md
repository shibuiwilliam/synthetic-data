# authoring_checklist.md — 執筆前・執筆後に必ず確認すること

> **新しい content を書くときは、着手前にこの全文を読むこと。**
> `docs/style_guide.md`（文体・架空化）と `docs/schema.md`（型）を置き換えるものではなく、
> **「lint が通っても残る欠陥」を潰すための追加チェックリスト**である。
> §1〜§4・§9〜§11 は yakkan-synth が 7 文書を書いて reviewer に通して得た教訓
> （`../insurance-contracts/docs/authoring_checklist.md`）の継承。§5〜§8 は契約書固有。
> **新たに見つけた欠陥はこのファイルに追記する（2 回同じ指摘を受けたら必ず）。**

---

## 1. 転載 — いちばん重い違反（lint は検出できない）

yakkan では **5 文書で同じ形の違反が再発した。** 契約書で危険な 5 つは `docs/style_guide.md` §2.1
（条の並び順・列挙の順序と語彙・別表の数値の列・様式の項目の並び・表記の癖）。

**対処**：

- **別表・目録の数値は必ず自分で作り直す。** 等差・等比にしない（作り物に見える）。端数を混ぜ、
  段数を実物と変える。
- **列挙は順序を入れ替え、語彙を 1 つ以上差し替える。**
- 「特定のひな型でしか見ない言い回し」を使わない。業界共通の定型（「〜をいう。」「ただし、〜を除く。」
  「本契約の成立を証するため」）は問題にしない。
- **判定軸ごと変える**のがいちばん確実（負担区分表の軸を「部位別」から「原因別」に変える 等）。
- **書き終えたら、条の並び・列挙・別表を読み返して「実物で見た形か」と自問する。
  見覚えがあるなら、それが模倣の証拠。**

## 2. 正解データ（gold）自体の誤り

`facts` と `alt` は **QA の正解そのもの**。間違っていると評価が壊れる。

- 図の `facts` に「◯◯は四つに分かれる」と書いたら、**本文を数えて確かめる**
  （yakkan では「四つの節」と書いて 6 節だった実例がある）。
- 図のノードラベルと本文の見出しを一致させる。**図だけ短縮した名前にしない。**
- 図・算式の中でも `{const:}` `{term:}` `{ref:}` が使える。**数値は必ず `{const:}` で書く。**
  生文字列で書くと定数を変えたときに取り残される（yakkan では 4 文書で起きた）。
  太字・ルビ・改行・脚注は SVG に形が無いので L06 が弾く。

## 3. 表・図は「導入文を持つ項の `blocks`」に入れる

条（`article`）直下の `blocks` に置くと、**導入文より前に描画される**。
「下表のとおり」が 2 段落上の表を指す状態になり、読み順・アンカーの QA が全滅する。
`dataset/<doc_id>/layout.json` の `pages[].reading_order` で順序を確認できる。

## 4. `meta.constants` の値を散らす

同じ値が複数の概念に使われていると数値 QA の弁別力が無くなる（yakkan では 30 日が 4 概念に使われていた）。

- 同一値の重複は**最大 2 件**まで。
- 宣言しただけで使わない定数を残さない。
- 本文にハードコードした数値を残さない（`{const:}` を通さないと L11 が効かない）。
- **制度上の代表値を避ける**（下請法の 60 日、遅延損害金 14.6%、消費税率、法定利率）。
  実在制度を指す値は転載の指紋と同じ問題を持つ（`docs/decisions.md` 2026-09-26 の 20）。

## 5. 当事者（契約書で最も多い欠陥）

**`{party:}` を使っていても論理の取り違えは機械検出できない。** 条ごとに確認する。

- **義務の主体が逆になっていないか。** 「乙は、甲に対し、委託料を支払う」——委託料を払うのは委託者（甲）。
  受託者・委託者、貸主・借主、売主・買主、開示者・受領者は**取り違えやすい**。
- **権利と義務が片方に偏っていないか。** 実物の契約書は双方に義務がある（一方的な文書は不自然）。
- 前文で導入した当事者を**全員使っているか**。導入したのに本文に出てこない当事者がいないか。
- 3 者契約では「丙」の役割（連帯保証人・保証会社）が**条文に実質を持っているか**
  （記名欄にだけ出てくる当事者は不自然）。
- 記名押印欄の名称・住所・代表者が当事者表示・前文と一致しているか（L19 は JSON を見る。
  **紙面は目視で確認する**）。後文が「各1通を保有する」と定める場合、`meta.copies` は当事者数と
  一致させる（L20）。当事者数を超える予備通を作るなら、その保有者を後文に明記する。

## 6. 契約書としての中身の整合（実務と矛盾させない）

法的助言ではなく「**読者が違和感を持たない程度の整合**」を目指す。

- **契約不適合責任（瑕疵担保）の期間**と、**検査・検収の期間**を混同しない（別の概念）。
- **所有権移転の時期**と**危険負担の移転時期**は別に定める（売買）。両方書くか、片方だけと決める。
- 秘密保持の**契約期間**と**義務の存続期間**を書き分ける（`nda` の主要な `apply` QA の土台）。
- 再委託を禁止しておいて、別の条で再委託先の義務を定めていないか（条文間の矛盾）。
- 解除事由に挙げた事象が、別の条で許容されていないか。
- 損害賠償の上限額を定めたなら、それを超える定めが他の条に無いか。
- 通知の方法（書面・電磁的方法）を定めたなら、他の条の「通知」もその方法に従うか。
- 賃貸借の**敷金の充当と返還**、原状回復の範囲（通常損耗を含むか）を矛盾なく書く。
- 様式型（`employment`）は**選択肢の組み合わせが矛盾しないか**（「期間の定めなし」に契約期間が書かれている等）。

## 7. 表・別紙と条文の対応を空振りさせない

- 一覧表が掲げる項目には**必ず対応する条文を置く**（逆も然り。yakkan では一覧に 5 つ挙げて条文が 3 つの例があった）。
- 本文の「別紙1に定める」に対応する別紙が**実在し、中身が空でない**か（L01 は存在しか見ない）。
- 頭書の値（賃料・期間・敷金）が本文の `{const:}` と一致しているか。
- 別紙の合計値が本文の代金・委託料と一致しているか（`purchase` の目録、`outsourcing` の報酬表）。
- **別紙・別表・様式の 3 系統を混ぜて使うときは、参照が正しい系統を指しているか**
  （「別紙1」と「別表1」は別物）。

## 8. `{ref:}` は「意味が合っているか」まで見る

lint は参照先の**存在**しか見ない。

- 「…の取扱いは第3項のとおり」と書いて、実際は第4項にも書いてあった（yakkan の実例）
- 「別紙に定める」と素の文字列で書き、別紙が 3 つあってどれか決まらなかった
  → **別紙への参照も必ず `{ref:sch1}` で書く**
- 前条・次条を「前条」と書きたくなるが、**`{ref:}` を使う**（build が「第4条（◯◯）」に解決する）

## 9. 定義語

- 定義した語は本文で**実際に使う**（L12 が拾うのは未定義使用だけで、死語は拾わない）。
- 同じ語を 2 か所で違う内容に定義しない。
- 定義の基準者をそろえる（「本件業務」を定義しておいて「委託業務」と書くと定義がカバーしない）。
- 章ごとに呼称を変えない（`{term:}` に統一）。

## 10. `records` を付ける

参照表（`definitions` / `fee_schedule` / `deliverables` / `inventory` / `head_matter` / `form_fields` /
`allocation` / `rate` / `procedure` / `mapping` / `history`）は `grid` と `records` の二重表現を持つ。

    uv run python scripts/fill_records.py content/<cid> --write

**結合セルのある表（頭書・負担区分表・記入欄）は機械導出できないので手で書く。**
列挙表（`enumeration` / `exclusions`）は参照表ではないので不要。

## 11. QA を書くときの型の選び方

`extract` / `table_lookup` / `definition` は **answer が evidence の平文に含まれていること**が L14 で
検査される。**要約した答えや算出値を書くとエラーになる。**

| 問いの形 | 型 |
|---|---|
| 本文・表から**そのまま**引ける | `extract` `table_lookup` `definition` |
| 表の中で**比べる**（どちらが負担するか・最大） | `table_reason` |
| 場面を与えて**規定を当てはめ、値を導く** | **`apply`**（包含検査の対象外。**自動生成できない唯一の型**） |
| 図の経路・隣接 | `figure_path`（答えは図に**実在するラベル**でなければ L14 が落とす） |
| 図の記述の真偽 | `figure_fact` |
| 参照先 | `crossref` ／ 数 | `count` ／ 存在しないもの | `negative` ／ ページ | `locate` |

**`apply` の算出値は機械で検算されない。** 自分で計算し、`HITL_TODO.md` の H5 に起票する。
配分（15 問・表 3・図 2・apply 2）は **L16 が error で強制する**——文章で書いただけでは守られない
（yakkan では 30 content のうち 13 が違反していた）。

## 12. 描画で踏む罠（内容の問題ではない）

- **`RenderLayoutError`**：本文の字数を数十字ぶん増減させると通ることが多い。ただし
  **構造を変えないと通らない形もある**。自分の書いた文が悪いと思って探索しすぎないこと。
  対処の順序：(1) 字数を増減、(2) 項の分け方を変える、(3) 別の style で描く。
- **「レンダリングが成功した」は「内容が全部載った」を意味しない。** 必ず `verify` を見る。
- 横長の表（頭書・目録・工程表）は列数を減らすか、行見出しの語を短くする。
- 枠つきブロック（`commentary`・囲み注）が**ページ境界で割れると続きが版面の外に出る**ことがある。
  長い解説は複数ブロックに分ける。
- `timeline` の軸目盛ラベルは両端に寄せて描かれる。`matrix` の列幅は列見出しに合わせて広がる。

## 13. 組み立てヘルパ `scripts/authoring.py`

parts の JSON を手で書くと、セルの id・`rowspan`・`records` を取り違えやすい。

| 関数 | 作るもの |
|---|---|
| `C` / `merged` | セル 1 つ／結合セルに飲み込まれた位置 |
| `table` | 見出し行 1 行の表（`records` も一緒に作るので `header_path` が取れる） |
| `enum_table` | 文と一体の列挙表（番号欄は `{auto_label}`。**キャプションを付けない**） |
| `art` | 条（項・号・条末脚注・ブロック） |
| `write` | UTF-8・indent 2・末尾改行で書く |

**検証はしない。** 書いたら `uv run keiyaku lint content/<cid>` を必ず通す。

## 14. 仕上げの手順

```
uv run keiyaku lint content/<cid>               # error 0 / warn 0 にする
uv run python scripts/fill_records.py content/<cid> --write
uv run keiyaku build content/<cid>
uv run keiyaku render content/<cid>             # style 省略時は blueprint の既定
uv run keiyaku verify dataset/<doc_id>          # error 0 / warn 0 にする
uv run keiyaku qa dataset/<doc_id>              # 自動 QA 30 問＋検証（**執筆 QA の L14 もここで初めて通る**）
uv run keiyaku manifest update
```

**`keiyaku qa` を `batch` の前に必ず挟む。** 執筆 QA の「answer が evidence の平文に含まれるか」（L14）は
`source` と `layout` が揃って初めて検査できるので、**`keiyaku lint` では通ってしまう**
（2026-09-27：`emp-0002` の「締切は毎月15日、支払の日は翌月5日」が 2 セルにまたがっていて batch で落ちた）。
答えは**evidence 1 つの平文に収まる形**に書く。

macOS では `DYLD_FALLBACK_LIBRARY_PATH=/opt/homebrew/lib` が要る（`make` 経由なら自動）。

**最後に PNG を全ページ自分で開いて見る**（`keiyaku review`）。**ページ数と lint が通っても崩れている
ことはある。** 目視でしか見つからない欠陥が実在する（yakkan：図の辺ラベルの重なり）。
