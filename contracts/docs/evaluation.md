## 1. 利用目的（設計の基準）

| # | 目的 | 評価したいこと |
|---|---|---|
| U1 | LLM / VLM のドキュメント読み取り精度 | テキスト＋構造内の位置づけ＋表と図の構造 |
| U2 | 読み取ったテキストの構造解析 | テキストが構造のどこに属するか（条・項・号、列挙の N 番目） |
| U3 | 読み取り結果の JSON 出力と採点 | 予測 JSON を採点できる形にデータが整理されていること |
| U4 | 検索エンジン（全文・ベクトル・ハイブリッド・ランク学習） | クエリ → ヒットすべきパッセージの対応（qrels） |
| U5 | **契約書に固有の抽出**（当事者・期間・金額・別紙の対応） | `{party:}` の解決結果・頭書と本文の対応・別紙参照 |

## 2. 継承する成果物と指標

### 2.1 文書ごとの評価向け成果物

| ファイル | 内容 |
|---|---|
| `elements.jsonl` | 1 行 1 要素の平索引。**評価スクリプトが最初に読む唯一のファイル**。kind・citation・parent_id・page・bbox・本文・表セルの意味座標・図ノードを 1 か所で引ける |
| `dataset/search/passages.jsonl` | 検索登録単位（条 1 パッセージ・長い条は項で分割・表 1 パッセージ・図は alt＋facts）。**コーパスは content ごとに 1 スタイル** |
| `dataset/search/queries.jsonl` | term / heading / scoped / qa の 4 系統。`related_truncated` / `n_related_total` で打ち切りを記録 |
| `dataset/search/qrels.jsonl` | grade 2（答えがそこにある）／1（関連。1 クエリ 20 件で打ち切り） |
| `dataset/README.md` | `keiyaku export` が**実測値を埋め込んで**生成する（固定文字列で焼き込まない） |
| `dataset/manifest.json` | 全文書一覧＋成果物一覧＋checksums。`keiyaku manifest check` が鮮度を検査し `make check` に入る |

### 2.2 読み取りの指標（`keiyaku eval`）
ページ別 CER／outline F1（label・title・page・citation・kind）／構造位置 coverage・citation 正解率
（**厳密一致と包含 `_contains` の併記**）／表 TEDS＋セル値 F1（`header_path` 経由の 3 つ組）／
図ノード・エッジ・経路 F1／列挙の順番つき一致／読み順 Kendall τ／bbox IoU／QA 一致。

### 2.3 検索の指標（`keiyaku eval --search-run`）
nDCG@1/5/10・Recall@1/5/10・MRR をクエリ種別ごとと全体で。
**`recall_ceiling@k`（到達可能上限）を必ず併記する**（適合が k 件を超えるクエリでは満点の並びでも 1 に届かない）。

### 2.4 コマンド
```
keiyaku eval dataset/<doc_id> --pred pred.json       # 1 文書の採点
keiyaku eval dataset/<doc_id> --oracle [--misread R] # 自己評価（満点／崩した満点）
keiyaku eval --all --oracle                          # 全文書
keiyaku eval --all --pred-dir <dir>                  # <doc_id>.json を拾って全文書＋平均
keiyaku eval --search-run run.json                   # 検索の採点
keiyaku export                                       # elements.jsonl / passages / search セット
```

## 3. 採点の原則（yakkan で確定済み。変えるときは decisions に記録）

1. **突合はすべて中身で行う。** 予測に内部 id は無い前提（QA のみ id）。テキストは正規化一致
   （NFKC＋空白除去）、見出しは (label, title)＋**出現回数**（**同名見出しの取り違え防止**——契約書は
   「（目的）」「（秘密保持）」「（協議）」が文書内・文書間で大量に重複するので、これが特に効く）、
   表・図は `caption_label` を**正規化してから**突き合わせる（全角「表１」と半角「表1」）。
2. **列挙として組んだ表は tables の母数に入れない**（`enumerations` 側で採点。二重に求めない）。
3. **列挙の項目は行頭番号を付けても付けなくても正解**（採点前に両側から落とす。**NFKC の前に**落とす）。
4. **予測の全キーは任意。** 無い観点は 0 になるだけで他は採点される。壊れた予測は黙って 0 点にせず、
   形の違いを警告として出す。
5. 自己評価の崩し（`--misread`）は**入れ子**にし、崩しの強さに対して指標が **recall で単調に悪化**することを
   テストで固定する（F1 は要素を落とすと precision が上がって跳ねる）。

## 4. 予測に使う語彙（契約書の差分）

基底仕様 §3（kind の一覧・`cells` の要否・図の種別ごとのノード粒度・`timeline` のエッジ 3 系統）を
**そのまま継承**し、次を追加する。**採点は完全一致なので、ここに書いていない語彙は当てようがない**
（yakkan では語彙未記載だけで kind 正解率が 0.0 になった実例がある）。

### 4.1 `outline[].kind` / `elements[].kind` の追加語彙

| 紙面 | kind |
|---|---|
| 前文（「◯◯と△△とは、…契約を締結する。」） | `preamble` |
| **頭書**（冒頭の当事者・物件・金額の一覧） | `head_matter` |
| 後文＋契約日＋記名押印欄（収入印紙欄を含む） | `signature` |
| 「別紙1」「別表1」「様式第1号」 | `appendix` |
| 「附則」 | `supplement` |
| **逐条解説の枠** | `commentary` |

既存語彙（`part` / `chapter` / `rider` / `section` / `article` / `paragraph` / `item` / `subitem` /
`subsubitem` / `appendix` / `appendix_section`）は基底仕様のとおり。

**`outline` に出すのは「番号を持つ節点」すべて**——条だけでなく**項（`２`）も号（`（１）`）も**出す
（gold は `第1条` → `２` → `（１）` と並ぶ。`dlg-0002` の実例で 73 件のうち条は 13 件しかない）。
見出し行だけを出すと、読めていても F1 が 0.3 程度に沈む（2026-10-02 の V-D で実測）。
`label` は紙面の番号、`title` は括弧の中の文言（無ければ空）。

**`bbox` は `elements[]` にだけ出す**。`tables[]` / `figures[]` にも `page` と `bbox` を書けるが、
**採点に使うのは `elements[]` の `bbox` だけ**（表・図の位置を測りたいときは、その表題や本文を
`elements` にも出す）。`figures[].nodes[].id` は**省いてよい**（省けばラベルが鍵になる）。
**`kind` は紙面の記号ではなく構造の深さ**：様式型（`employment`）でも、いちばん外の区分（「1 労働契約の期間」）が
`chapter`、その下の「(1)」が `article`、その中の「①」が `paragraph`。**迷ったら出さない**（`null`）。

### 4.2 citation の書式

基底仕様どおり「**紙面の番号だけを連ねた文字列**」。条は通し番号なので、
**章を持つ doctype（`sysdev`）だけ章を冠す**（`contracting` は章を持たない）。

| doctype 群 | 例 |
|---|---|
| 条文型・頭書型・目録型 | `第4条 2 (1)` ／ 細目まで `第4条 2 (1) ア` |
| 章立て（`sysdev`） | `第2章 第7条 2`（**章を冠す**。gold の実測：`第1章 第1条 2`。`caption_numbering: chapter` の文書） |
| 約款型（`contracting`） | `第三条 2 (1)`（**漢数字・章を持たない**。条見出しが条番号の上に来る体裁でも、位置づけに条番号を二重に入れない） |
| 様式型（`employment`） | `1 (2) ①` |
| 別紙・附則の中 | `別紙1 2` ／ `附則 2` |
| **頭書の中** | `頭書 1` ／ `頭書 1 (2)`（頭書は番号を持たないので**呼び名**で指す。`docs/schema.md` §11.1） |

### 4.3 当事者・記名押印欄
- 本文中の「甲」「乙」は**紙面の文字どおり**書き起こす（`{party:}` は生成側の機構であり、
  読み取り側は解決後の文字列を出す）。
- 記名押印欄・当事者表示の行は **`pages[].text` に紙面どおり入れる**。「印」の文字も含む。
- **`elements` に出すかどうかは任意**——gold 側のこれらの要素は**テキストを持たない**
  （名称・住所・代表者は `meta` から描画されるため）ので、**出しても出さなくても点は動かない**。
  §4.9 の「採点される要素」を見ること。
- 当事者の同定（「甲＝株式会社◯◯」）を測りたいときは `qa` の `extract` / `definition` で問う
  （**予測 JSON に当事者専用のキーは足さない**。v1 は語彙を増やさない）。

### 4.4 頭書・記入欄の表
- 頭書（`head_matter`）と記入欄（`form_fields`）も `tables` に出す。
  **`cells`（行見出し・列見出し・値の 3 つ組）を必ず出す**——`grid` が完全一致（TEDS 1.0）でも
  `cells` を出さなければ表セル F1 は 0 になる。
- チェックボックスは**セルの文字として**書き起こす（`☑ 期間の定めなし` をそのまま）。
  選択結果だけを書くのではない（`records` は gold 側の意味表現で、予測に求めるのは紙面の文字）。

### 4.5 `pages[].text` に何を入れるか

**紙面の読み順どおりに連結する。** 本文だけを先に並べて表や見出しを後ろにまとめると、
**読めていても CER が 0.6 まで跳ねる**（2026-10-02 の V-D で実測）。
CER は編集距離なので、**並べ替えは誤字より重い**。

| 紙面のもの | `pages[].text` | 備考 |
|---|---|---|
| 本文・見出し・番号 | **入れる** | `1　用語の意味(1)　用語①この通知書において…` と紙面の順に |
| 表のセル | **入れる** | 表題（`表1　用語の意味`）の直後に、行→列の順で |
| **図の中の文字** | **入れない** | 図は `figures[]` に出す。入れると余分な文字として CER が上がる |
| **奥付**（最終ページの罫線の下） | **入れる** | 文書名・契約書番号・連絡先・但し書き |
| 柱（各ページ上端の文書名） | 入れない | 版面の装飾であって内容ではない |
| ノンブル・ページ下端の整理番号 | 入れない | 同上 |

### 4.6 図のノードの粒度（種別ごと）

`figures[].nodes` に何を出すかは種別で決まる。**箱の中の小さな文字もノード**になる種別がある。

| 図の種別 | ノードにするもの |
|---|---|
| `flowchart` | 箱・ひし形ごとに 1 ノード（辺のラベルはノードではない） |
| `steps` | **段階ごとに 1 ノード ＋ 小枠の各行**（「前月の10日前まで」「事業主が示す」もノード） |
| `tree` | 節点ごとに 1 ノード |
| `timeline` | 目盛・期間（span）・出来事（event）のラベルごとに 1 ノード |
| `matrix` | 行見出し・列見出し（印はセルの値であってノードではない） |

経路（`paths`）は**段階の本線だけ**（`steps` なら小枠を含めない）。

### 4.7 逐条解説（`commentary`）（**2026-09-27 実装済み**）
- 解説枠は `elements` に `kind: "commentary"` で出す。**本文（`article` / `paragraph`）と混ぜない。**
- `layout.pages[].text_lines[].region` が `"commentary"` になる（`docs/schema.md` §11.3）。
- `pages[].text` には紙面どおり**含める**（紙面にあるものは正解テキストに入れる原則）。
  読み取り側に分離を求めるのは `region` と `kind` のほうであって、本文テキストからは落とさない。
- 検索パッセージは `kind: "commentary"` の**別パッセージ**になる（`keiyaku/search_set.py`）。
- 解説の段落は `derived.plain_text` に `<block>__p{i}` の id で入るので、**QA の evidence に指定できる**
  （「解説によれば〜」型の設問が書ける。`content/lic-0002` の `qa_auth_012` `qa_auth_013`）。
- **v1 では `license` の 1 variant（`lic-0002`）にしか出ない。母数が小さいことを報告に必ず併記する。**
  実測：パッセージ 202 件のうち `commentary` は 10 件。

### 4.8 読み手がよく迷うところ（**盲検で実際に出た 20 件**。2026-10-02／10-03）

構築経緯を知らない読み手に `pages/*.png` とこの文書だけを渡して読ませたところ、
**点は出たが「仕様のどこにも書いていない」と報告された**項目が 16 件あった。
gold の実測に合わせてここで決める（`docs/validation_plan.md` §4 の実施記録）。

| 迷うところ | 出し方（gold の実測） |
|---|---|
| 逐条解説の `citation` | **空文字**。解説は紙面の番号を持たない |
| 解説枠の見出し行（「解説」） | **出さない**（gold は内部に `commentary_title` を持つが、予測の語彙には無い） |
| 解説を `outline` に出すか | **出さない**（番号を持たないため。`kind` の enum に `commentary` はあるが `elements` 用） |
| 別表・別紙の中の「1」「2」 | `paragraph`（`appendix_section` は紙面に出ない無番号の節） |
| 別表の citation | **紙面どおり**（`別表1 2`。`別紙` に正規化しない） |
| 表題・図題の行 | **番号つきの行そのもの**（「表1　用語の意味」）は gold に無い。**文言だけ**（「用語の意味」）の要素は gold にあり、出すと bbox の採点対象になる |
| 条見出しの行 | 同上。「第1条（目的）」という行は gold に無く、**title だけ**（「目的」。`kind: article`）の要素がある |
| 奥付（最終ページの罫線の下） | `pages[].text` には**入れる**。`elements` に出すかは任意で、`kind` は採点されない（`null` でよい） |
| 当事者表示（「開示者　◯◯」の 2 行） | `kind: "paragraph"`。**`head_matter` ではない**（頭書は番号つきの項目か表を持つもの） |
| `pages[].text` の項番号・号番号 | **入れる**（§4.5）。実例が番号を落としていたら実例のほうが誤り |
| CER の比較 | **正規化後**（NFKC ＋ 空白除去）。全角・半角、空白の有無では落ちない |
| `bbox` の矩形 | **1 要素 1 矩形**。左右は**段の端**、上下は先頭行の上端〜末尾行の下端（行ボックス） |
| `figures[].nodes[].role` | 採点に使わないので `null` でよい。gold の語彙は `flowchart`＝`start`/`process`/`decision`/`end`、`timeline`＝`tick`/`span`/`event`、`steps`＝`step`/`detail`/`ask`、`tree`＝`tree` |
| `timeline` のエッジ 3 系統 | `next`（目盛→次の目盛）／`from`・`to`（期間の両端→目盛）／`at`（出来事→目盛） |
| `steps` の小枠の見出し（「内容」「行うこと」） | **ノードにしない**（値の行だけがノード。`relation` は `detail` / `ask`） |
| `cells` に行見出しの列そのもの | **出さない**（行見出しは各セルの `row_headers` に入る） |
| 頭書の番号つき項目（「1 品名及び数量」） | 項目名が `item`、その下の記載が `paragraph`。どちらも citation は `頭書 1` |
| `steps` の小枠の 2 行 | 上段（「内容」の行）が `detail`、下段（「行うこと」の行）が `ask` |
| 前文 | 節点そのものは `preamble`（テキストを持たない）。**本文の段落は `paragraph`** で、これは採点される |
| 2 段に並んだ記名押印欄の読み順 | 左の段をすべて読んでから右の段（列優先） |
| 当事者表示が**罫線の表**に見えるとき | `tables` に**出さない**（gold は表ではなく当事者の枠として持つ。出すと表セル F1 が下がる） |
| ページをまたいで**繰り返されるヘッダ行** | `pages[].text` には **1 回だけ**入れる（gold は繰り返しを含めない） |
| 前文の段落に番号（`①`）が付いているとき | **`outline` に出す**（番号を持つ節点はすべて出す。番号が無ければ出さない） |
| `timeline` の `paths` | **目盛の連なり 1 本**（`始業→休憩の開始→…→終業`） |
| `citation` の比較 | **NFKC 正規化後**。全角でも半角でもよい（`第２条 （１）` と `第2条 (1)` は同じ） |
| 様式型の 4 階層目（`ア`） | citation に**入れる**（`3 (2) ② ア`） |
| 目次（`sysdev` のような長文型） | 本文は `pages[].text` に**入れる**（ページ番号も紙面どおり）。`elements` と `outline` には**出さない** |

**形式の実例は手で書かない。** `uv run keiyaku eval dataset/<doc_id> --oracle --dump-pred <path>` で
**正解から作った満点の予測**を書き出せる。手書きの実例は規約からずれる（この盲検で、配った実例が
`pages[].text` の項番号を落としていて読み手を迷わせた）。

### 4.9 どの要素が採点されるか（**出す／出さないで点が動くのはどれか**）

`elements` のうち**採点に効くのは、本文の項・号**（gold が `paragraph` / `item` / `subitem` /
`subsubitem` の `label` を持つもの）。**前文の段落・後文（「本契約の成立を証するため…」）・
頭書の中の記載の行・別紙の項**もここに入る。ここだけが「構造位置 カバー率／citation 正解率／
種別正解率」と bbox の対象になる。

**bbox（IoU・当たり率）の対象はもっと広い**——`derived.plain_text` に入るものすべて、すなわち
**表のセル・図のノードのラベル・条見出しの title・表題の文言・逐条解説の段落**も含む。
出せば当たり、出さなければその分だけ母数から外れる（precision は下がらない）。

**次のものは gold 側に突合できるテキストの要素が無いので、`elements` に出しても出さなくても
構造位置の点は動かない**：

- 条見出し・章見出しの**番号つきの行**（「第1条（目的）」）——title だけの要素は gold にある
- 表題・図題の**番号つきの行**（「表1　用語の意味」）——文言だけの要素は gold にある
- 表のセル（構造は `tables[].grid` と `cells` で採点する。**bbox では採点される**）
- 当事者表示（「委託者　◯◯」）と記名押印欄の各行（住所・名称・代表者・印・収入印紙・契約日）
  ——**後文の文（「本契約の成立を証するため…」）は本文の段落なので採点される**。混同しない
- 奥付（最終ページの罫線の下）
- 頭書の**項目名**（「1 品名及び数量」）——その下の**記載の行**（「冷凍食品の…一式」）は採点される

**ただし `pages[].text` には紙面どおり入れる**（§4.5 の表）。CER はページ全体の文字列で測るので、
ここを落とすと点が下がる。**「要素に出すか」と「ページ本文に入れるか」は別の話**（2026-10-03 の盲検で、
この 2 つが混ざって読み手が迷った）。

## 5. doctype 別の観点の効き方（バッチ設計・報告の指針）

全 doctype で同じ指標を計算するが、文書の性質で母数が偏る。報告は**doctype 別＋全体**で出し、
母数が小さい観点は件数を併記する。

| doctype 群 | 厚い観点 | 薄い観点 |
|---|---|---|
| 条文型（nda / outsourcing / delegation / consulting） | 構造位置（通し条番号）、当事者文字列、列挙、記名欄の bbox | 表（1〜3 点）、図（1 点） |
| 頭書型（lease） | **表の意味座標**（頭書・分担表）、本文と表の値の対応、読み順 | 図 |
| 目録型（purchase / license） | 表 TEDS・セル F1、数値の抽出 | outline の深さ |
| 様式型（employment） | **表セル F1**、bbox、チェックボックスの読み取り | outline（浅い）、参照関係 |
| 長文型（contracting / sysdev） | 深い outline、目次のページ一致、ヘッダ章名、読み順 | — |

**同名の条（「目的」「定義」「協議」「合意管轄」）が doctype を横断して大量に現れる**ため、
`scoped` クエリ（文書名＋見出し）の弁別評価は yakkan より厳しくなる＝**評価として良質になる**。
コーパスへの混入単位は「content ごとに 1 スタイル」を維持する。

## 6. 何をもって「評価データとして使える」とするか（DoD。P6〜P7 で判定）

yakkan が到達した水準を合格ラインとして継承する：

1. `keiyaku eval --all --oracle` が**全文書・全指標で満点**。
2. `--misread` で崩すと全指標が **recall 基準で単調に悪化**（テストで固定）。
   図が 1 点しかない文書では図の指標が動かないことがある——**図が 3 点以上ある文書で単調性を測る**。
3. **PDF だけを読む規則ベースの読み取り器**（`scripts/baseline_reader.py`）で全文書を採点でき、
   点が 0 と 1 の間で動き、文書の性質（doctype・style）で差が出る。
4. **構築文脈を持たない読み手による盲検読み取り**（`docs/validation_plan.md` §4）を
   **骨格類型ごとに 1 本以上**（条文型・頭書型・様式型・長文型）通し、発見された契約の穴をすべて解消済み。
5. `manifest check` が実ファイルと一致。`make check` 緑。
