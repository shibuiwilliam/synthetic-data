# style_guide.md — コンテンツ生成（執筆）ガイド

> 執筆・`library/clauses/`・QA 作成の作業では、**着手前に必ず本ファイルと `docs/authoring_checklist.md` を
> 読む**こと（後者は「lint が通っても残る欠陥」の一覧）。
> 執筆プロトコル（scaffold → 執筆 → lint → fill_records → build → render → verify → review → qa）は
> CLAUDE.md §7。型は `docs/schema.md`、doctype ごとの必須要素は `docs/doctypes.md`。

## 1. 役割分担

- **Python**：骨組み（scaffold）、番号・当事者呼称・参照・目次・ヘッダ経路の導出、lint、描画、検証、自動 QA。
- **Claude**：条文本文、定義、表の中身、図のノード・エッジ、脚注・注記、逐条解説、`alt` / `facts`、執筆 QA。
- 執筆者が**書いてはいけないもの**：
  - 番号ラベル（「第1条」「(1)」「①」「ア」）→ ツリー位置から build が導出
  - **当事者呼称**（「甲」「乙」「委託者」）→ `{party:client}` `{party:client|role}`
  - 表・図番号（「表2」「図1」）→ `{ref:tbl_fee}` `{ref:fig_flow}`
  - 別紙番号（「別紙1」）→ `{ref:sch1}`
  - `derived`、目次、ページ番号、後文の通数（`meta.copies` から）、契約日（`meta.contract_date` から）
- 表・列挙表・条の組み立ては `scripts/authoring.py` を使う。**ヘルパは検証しない**——書いたら必ず
  `keiyaku lint content/<cid>` を通す。

## 2. 架空化ルール（lint L08 / L19 で強制）

| 対象 | 規則 |
|---|---|
| 会社名・屋号・サービス名・商品名 | 架空。実在名は `keiyaku/lint/denylist.txt` で検出。実在名の「もじり」（1 字違い・読みが同じ）も禁止 |
| 士業法人名（法律事務所・税理士法人） | 架空（参考にしたひな型の配布元名を絶対に書かない） |
| 人物名（代表者・担当者・労働者） | 架空。実在の著名人と同姓同名を避ける |
| 住所 | **架空の町名・番地**（「東京都千代田区丸窓町一丁目1番1号」のように実在しない町名）。都道府県・市区は実在可 |
| 物件名・所在地（lease） | 架空。登記情報らしい記載（地番・家屋番号）も架空の番号にする |
| 登録番号（license） | 架空（「特許第9,999,999号」のように**実在しない桁・番号**にする。HITL で最終確認） |
| URL / メール | `example.jp` `example.co.jp` `example.com` のみ |
| 電話番号 | ゼロ埋めのみ（`0120-000-000` `03-0000-0000`） |
| 金融機関・口座 | 架空の銀行名・支店名。口座番号はゼロ埋め |
| 法令・裁判所・官公庁 | 実在の**名称のみ**可（「民法」「下請代金支払遅延等防止法」「東京地方裁判所」）。**法令の条番号は書かない**（CLAUDE.md §15） |
| 契約書番号・様式番号 | 架空 |
| 金額・日付・期間・率 | 架空だが文書内で一貫（`meta.constants` ＋ `{const:}`、L11）。**同一値の使い回しは 2 概念まで**。**値は紙面の他の値の部分文字列にならないように選ぶ**（`5パーセント` は `25パーセント` の中に、`4回` は `第4回` の中に現れて L11 が誤検知ではなく**本当に紛らわしい**——2026-09-27 `con-0002`）。実務の代表値（下請法の 60 日、遅延損害金 14.6%、消費税率 等の**制度上の値**）は、実在制度を指すので**使わずに架空の値にする**か、制度を指さない形に書き換える |
| disclaimer | 文書末尾（colophon）に「本書は読み取り検証用に生成された架空の契約書であり、実在の当事者・取引とは関係がなく、法的効力を有しない。」相当の定型文を必ず入れる。**ページごとには入れない** |

### 2.1 転載の指紋（最重要。機械では検出できない）

**模倣は「文章」より先に「構造の細部」に出る。** 契約書で特に危険なのは次の 5 つ：

1. **条の並び順**：参考ひな型の第1条〜第20条の順序をそのまま辿ると、文章を全部書き換えても骨格が同一になる。
   → 章・条の順序を変える。一般条項の置き場所（冒頭か末尾か）を変える。条をまとめる／割る。
2. **列挙の順序と語彙**：秘密情報の例外（公知・独自開発・第三者から正当に取得・開示前に保有）、
   禁止事項、免責事由の**並びと語形**。→ 順序を入れ替え、**語彙を 1 つ以上差し替える**。
3. **別表・目録の数値の列**：料率の段（5%・3%・1%）、負担区分表の項目の並び、部分払の割合。
   → 自分で作り直す。**等差・等比にしない**（作り物に見える）。端数を混ぜ、段数を実物と変える。
4. **様式の項目の並び**（`employment` が特に危険）：厚労省様式の項目順と語形は、それ自体が指紋。
   → 項目の順序を変え、語形を言い換える（「始業、終業の時刻」→「勤務の開始時刻および終了時刻」）。
5. **表記の癖**：交ぜ書き、送り仮名、括弧の種類、「乙は、甲に対し、」の読点の打ち方までが一致すると指紋になる。
   → 自分の表記規則（§3.1）を決めて全文で通す。

業界共通で避けられない定型（「〜をいう。」「ただし、〜を除く。」「〜しなければならない。」
「本契約の成立を証するため」「協議のうえ、これを解決する。」）は**問題にしない**。
問題は、**特定のひな型でしか見ない言い回し・構成そのまま・実在の条見出しの並び**である。

**書き終えたら、列挙と別表と条の並びを読み返して「実物で見た形か」を自問する。見覚えがあるなら、
それが模倣の証拠。**

## 3. 文体（全 doctype 常体。lint L10 が文末形の統計で判定）

### 3.1 表記規則（1 文書内で必ず統一する）
- 文末：「〜とする。」「〜しなければならない。」「〜することができる。」「〜ものとする。」。
  **敬体（「〜します」「〜ください」）を混ぜない。**
- 主語は `{party:}`。「甲は、乙に対し、〜」のように**読点で区切る**（法文の慣行）。
- 「及び／並びに」「又は／若しくは」を**正しく使い分ける**（並列が 2 段になるとき、小さい方に「及び」「又は」、
  大きい方に「並びに」「若しくは」）。誤用は実物らしさを壊す。
- 期間は「〜から起算して◯日」「◯日以内」「◯か月」。**起算点を必ず書く**（`apply` QA の土台）。
- 金額は `digit_style` に従う。「金1,000,000円」型と「100万円」型を混在させない。
  消費税の扱い（内税／外税）を明記する doctype では全箇所で揃える。
- 但し書きの入れ子は **2 段まで**。1 文が長くなるのは実物どおりで構わないが、係り受けは明確にする。
- 条見出しは**体言**（「（目的）」「（秘密保持）」「（契約不適合責任）」）。動詞止めにしない。

### 3.2 定義
- 「本契約において『◯◯』とは、〜をいう。」。定義は第2条に集めるか、各章の冒頭に置く（doctype の variant）。
- 定義した語は本文で**実際に使う**（L12 が拾うのは未定義使用だけ。死語は自分で消す）。
- 同じ語を 2 か所で違う内容に定義しない。章ごとに呼称を変えない（`{term:}` に統一）。

### 3.3 一般条項
`library/clauses/` に型を置いてよいが、**文言は文書ごとに変える**（L15 が文単位重複 30% 超で警告）。
協議・合意管轄・通知・存続・反社・権利義務の譲渡禁止・完全合意・可分性・準拠法。
**全部入れると「テンプレを並べただけ」に見える**——doctype と題材に合うものを 4〜8 条だけ選ぶ。

### 3.4 様式型（`employment`）の文体
- 条文体ではなく**記入様式の文体**。項目名は体言（「契約期間」「就業の場所」）、
  記載内容は名詞句・体言止め（「本社営業部」「午前9時00分から午後6時00分まで」）。
- 選択欄は「☑ 期間の定めなし／□ 期間の定めあり（　年　月　日から　年　月　日まで）」の形。
  **空欄を残さない**（読み取り正解が空文字になる要素を作らない）。

## 4. 本物らしさの密度要件

- 読者が斜め読みして「テンプレを埋めただけ」と感じる文書は**不合格**。各条に具体的な数値・期間・手続き・
  例外が入っていること（NDA なら「開示後3年間」「書面による事前承諾」「複製は1部まで」）。
- **表・図は本文と噛み合っていること**：本文が「別紙1に定める」と言ったら別紙1が実在し（L01）、
  表の値が本文の数値と一致する（L11）。**一覧表が掲げる項目には必ず対応する条文を置く**（逆も然り）。
- 表・図は**導入文を持つ項の `blocks`** に入れる。条（article）直下に置くと**導入文より前に描画され**、
  「下表のとおり」が 2 段落上の表を指す状態になって読み順・アンカーの QA が全滅する（L22）。
  **脚注ブロックも同じ**——`{fn:n}` を書いた項より前の項に付けると注記が参照の上に出る（L02）。
  脚注は**条の末尾の項**か**条そのもの**に付ける（条に付けたものは条末に描かれる）。
- **1 つの条に列挙を 2 組以上置くときは、号をそれぞれの導入文の `children` に入れる**（L23）。
  兄弟に並べると 2 組目が `(1)` ではなく `(7)` から始まる。
- **条見出し（`node.title`）にはトークンを書けない**（RichText ではない）。呼称が役割名の doctype で
  「（発注者の解除権）」のような見出しを書くと L19 に当たる。**alias は「甲」「乙」にし、役割名は
  `role_label` で持つ**こと（`docs/decisions.md` 93）。
- **`{term:}` は語を太字にするだけで、定義の文は紙面に出ない。** 定義条（散文）か定義表を置くこと（L12）。
  さらに `defined_terms[].definition` は**正解データ**なので、紙面に印字した文言と揃える。
  食い違っていると、紙面から答えた読み手が不正解になる。トークン（`{party:}` `{term:}`）も同じものを使う。
- `{ref:}` は参照先の**存在**しか lint されない。**意味が合っているか**（指した項に本当にその規定があるか）は
  執筆者と reviewer が見る。
- 図の `alt` / `facts` は **QA の正解そのもの**。「◯◯は四つに分かれる」と書いたら本文を数えて確かめる。
  図・算式の数値は必ず `{const:}` で書く（生文字列は定数変更に追従しない）。
- 参照表（`definitions` / `fee_schedule` / `deliverables` / `inventory` / `head_matter` / `form_fields` /
  `allocation` / `rate` / `procedure` / `mapping` / `history`）には `records` を付ける
  （`scripts/fill_records.py`。**結合セルのある表は手で書く**）。列挙表（enumeration / exclusions）は不要。
- 同一 doctype の複数文書では**題材（業種・目的物・サービス）・当事者・条構成・数値**を変える。
  `lint --similarity` を執筆完了ごとに実行する。

## 5. QA 執筆（1 文書 15 問。L16 が配分を強制）

種別は基底仕様の 11 種。**表の問い（`table_lookup`＋`table_reason`）3 問以上・図の問い
（`figure_path`＋`figure_fact`）2 問以上・`apply` 2 問以上・件数ちょうど 15**（blueprint の `authored_qa` で変更可）。

| 問いの形 | 型 |
|---|---|
| 本文・表から**そのまま**引ける | `extract` `table_lookup` `definition`（**answer が evidence の平文に含まれること**を L14 が検査） |
| 表の中で**比べる**（最大・最小・どちらが負担するか） | `table_reason` |
| 場面を与えて**規定を当てはめ、値・結論を導く** | `apply`（包含検査の対象外。**執筆 QA でしか作れない**） |
| 図の経路・隣接／記述の真偽 | `figure_path`（答えは図に**実在するラベル**）／`figure_fact` |
| 参照先／数／存在しないもの／ページ | `crossref`／`count`／`negative`／`locate` |

契約書で書きやすい `apply` の題材（**各 doctype に 2 問**）：

- 検収期限（「乙が2026年5月10日に納品し、甲の検査期間が10営業日のとき、検収の期限はいつか」）
- 解約・更新拒絶の通知期限の逆算（「2027年3月31日で終了させるには、通知はいつまでに発するか」）
- 遅延損害金・日割賃料の計算（率と日数を本文・表から引いて掛ける）
- 実施料の算出（売上区分 × 料率）／割増賃金の計算（基本給と割増率）
- **秘密保持義務の存続期間**（「2026年4月1日に開示された情報は、いつまで秘密として扱うか」
  ——契約期間と存続期間を混同すると誤答になるよう設計する）

`evidence` は必ず存在する要素 id を指す（L14）。書いたら `keiyaku qa --validate` を通す。
**`apply` の算出値は機械で検算されない**——自分で計算し、`HITL_TODO.md` の H5 として人間の確認に回す。

## 6. 執筆チェックリスト（詳細は `docs/authoring_checklist.md`）

`review`（全ページ PNG を目視）のときに必ず見る、契約書固有の項目：

1. **当事者の取り違え**：甲がすべき義務が乙になっていないか。`{party:}` を使っていても**論理の取り違えは
   lint で検出できない**。条ごとに主語を確認する。
2. **記名押印欄**：当事者表示・前文・記名欄の名称／住所／代表者が一致して**描画されている**か
   （L19 は JSON を見る。紙面は目視で確認する）。後文の通数と記名ブロック数が合っているか。
3. **頭書と本文**：頭書の賃料・期間・敷金が本文の `{const:}` と一致しているか。
4. **別紙**：本文の「別紙1に定める」に対応する別紙が実在し、**中身が空でない**か。
5. 契約書らしくないページ割れ（後文と記名欄の分離、条見出しだけがページ末尾に残る）がないか。
6. **様式型**：選択欄の ☑ が同一項目で 2 つ以上付いていないか。空欄が残っていないか。
7. disclaimer が末尾にあるか。**本文中に「架空」「サンプル」の断り書きが漏れ出していない**か。

新たに見つけた「lint が通っても残る欠陥」は `docs/authoring_checklist.md` に追記する
（**2 回同じ指摘を受けたら必ず**）。

## 7. 描画で踏む罠（内容の問題ではない）

- `RenderLayoutError` は内容の高さが特定の「**帯**」（yakkan 実測 48 字幅）に一致したときだけ起きる。
  対処の順序：(1) 字数を帯の幅**以上**増減、(2) 項の分け方を変える、(3) 別の style で描く。
  **自分の文が悪いと思って探索しすぎない。**
- 横長の表（頭書・目録・工程表）は列数を減らすか行見出しの語を短くする。段組は使わないので
  `span_columns` は不要（使わない）。
- **「レンダリングが成功した」は「内容が全部載った」を意味しない。** 必ず `verify` を見る。
- 「fragment はあるのに PDF にテキストが無い」ときは bbox が版面の外（マージン帯）に出ていないか見る。
