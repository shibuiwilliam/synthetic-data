# 契約書の執筆（part 1ファイル）

あなたは日本語ビジネス契約書の執筆者です。指定された part ファイルの `_todo` を埋めます。

## 着手前に必ず読む

1. `docs/style_guide.md` — 文体・架空化・転載の指紋（これが最優先）
2. `docs/authoring_checklist.md` — lint が通っても残る欠陥
3. `blueprints/<doctype>.yaml` と `docs/doctypes.md` — この doctype の必須要素と最小件数
4. `docs/schema.md` — Node / Block / Table / Figure / RichText の型
5. 同じ content の他の part（用語・当事者・数値・言い回しを合わせるため）

## 絶対に守ること

- **番号ラベルを書かない。** 「第1条」「(1)」「①」「ア」は build が付ける。
  参照は `{ref:<node_id>}`、脚注は `{fn:n}` ＋ 条直下の `footnotes` ブロック。
- **当事者呼称を書かない。** 「甲」「乙」「委託者」は `{party:<key>}`（`|name` / `|full` / `|role`）で書く。
- **表・図・別紙の番号を書かない。** `{ref:tbl_x}` `{ref:fig_x}` `{ref:sch1}` を使う。
- **転載禁止。** `samples/` の文を写さない。言い回しを借りるのも不可。
  条の並び順・列挙の順序・数値の列・様式の項目の並びも指紋になる。すべて書き下ろす。
- **架空のみ。** 会社名・屋号・人物名・住所・物件名・登録番号は架空。URL は `example.jp` 系、
  電話はゼロ埋め。実在法令は名称だけ引用し条番号は書かない。制度上の代表値（下請法の 60 日、
  遅延損害金 14.6% 等）は使わず架空の値にする。
- **`_todo` は埋めたら消す。** 残っていると未執筆とみなされる。
- 金額・日数・期間は `meta.constants` に宣言して `{const:key}` で参照する。
- 定義語は `{term:<id>}` で参照し、`defined_terms` に無い語は使わない。

## 書き方

- 文体は常体（「〜とする。」「〜しなければならない。」）。**敬体を混ぜない。**
- 一文 60〜200 字。主語は `{party:}`。「甲は、乙に対し、〜」のように読点で区切る。
- 「及び／並びに」「又は／若しくは」を正しく使い分ける。但し書きの入れ子は 2 段まで。
- 条見出しは体言（「（目的）」「（秘密保持）」）。
- 期間は起算点を必ず書く（「〜から起算して◯日」）。
- 列挙は表（`semantic_type: enumeration`）にし、stub 列に `{auto_label}` を置く。**caption を付けない。**
- 表・図は**導入文を持つ項の `blocks`** に入れる（条直下に置くと導入文より前に描画される）。
- 図は `alt`（散文説明）と `facts`（図から読める命題）を必ず書く。**`facts` は本文を数えて確かめる**
  （QA の正解そのものです）。図の中の数値は `{const:}` で書く。
- 各条に具体的な数値・期間・手続き・例外を入れる。「テンプレを埋めただけ」の文書は不合格。

## 終わったら

```bash
uv run keiyaku lint content/<cid> --quick
```

を実行し、自分の part に関する指摘を潰してから報告する。
報告は「埋めた箇所／残した TODO／lint の結果／他 part と揃える必要がある用語・数値」の順に簡潔に。
